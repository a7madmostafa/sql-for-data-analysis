What you'll be able to do after this lesson

  • Recognize a SQLite-only convenience (the bare-column MAX() guarantee) and choose the portable pattern instead, because it's what will actually work on MySQL too.
  • Chain a 3-4 table JOIN through two views without rewriting the join logic each time.
  • Combine a team's home and away results into one column with UNION ALL before aggregating — the same shape Day 06 used, applied to a new problem.
  • Turn a correlation into an actual business caveat: a style stat that doesn't predict the outcome you care about isn't worth recommending, no matter how good it looks in isolation.
  • Spot a data-coverage gap with an anti-join before it becomes an unanswerable question from a stakeholder.

Marcus does recruitment analytics for a Championship club. Six weeks before the January transfer window, his technical director wants two things on his desk: a shortlist of attacking targets worth a scouting trip, and a read on how the leagues they might buy from actually play.

The club's data team also feeds a small betting newsletter on the side, so there's a third ask tacked on at the end — is "favorite" actually worth anything? There's no new SQL syntax in this project: it's Days 01-04 (filtering, aggregation, JOINs, views, window functions, the anti-join pattern) applied to a real dataset of European football matches, players, and teams that wasn't built with any of these exact questions in mind.

•The dataset

Source: European Soccer Database by hugomathien on Kaggle — 25,979 matches, 11,060 players, and 299 teams across 11 European countries, 2008-2016, plus FIFA-style player and team attribute ratings and Bet365 betting odds for most matches. 7 real tables (an 8th, sqlite_sequence, is SQLite's own internal bookkeeping, not data) — project_07.ipynb's setup section previews every one before Marcus's questions start.

Download it before you start — not committed to this repo

soccer.sqlite is ~299 MB — over GitHub's 100 MB limit, so like Day 06's NBA dataset, it isn't checked into this repo.

1. Go to the dataset page and click Download (a free Kaggle account is required), or with the Kaggle CLI: kaggle datasets download -d hugomathien/soccer.

2. Unzip it — the file inside is named database.sqlite; rename it to soccer.sqlite.

3. Place it in the shared Databases/ folder at the repo root: Databases/soccer.sqlite — every database this course uses, MySQL or SQLite, lives there. project_07.ipynb connects with a relative path (sqlite:///../Databases/soccer.sqlite).

Databases/*.sqlite is git-ignored for files this large — once it's downloaded, there's nothing to commit, just re-download if you ever lose the file.

•Two views, reused everywhere

Player_Attributes and Team_Attributes both carry one row per player/team per rating date, not one row per entity — so almost every question above needs a "current" view defined once, up front, the same CREATE VIEW pattern from Day 04:

project_07.ipynb
%%sql DROP VIEW IF EXISTS current_player_ratings; CREATE VIEW current_player_ratings AS SELECT * FROM ( SELECT p.player_name, a.overall_rating, a.finishing, a.sprint_speed, ROW_NUMBER() OVER (PARTITION BY a.player_api_id ORDER BY a.date DESC) AS rn FROM Player p JOIN Player_Attributes a ON p.player_api_id = a.player_api_id ) WHERE rn = 1;
Why a window function, not GROUP BY + MAX(date)

SQLite has a documented special case: when a query has exactly one MIN()/MAX() aggregate, every other selected column is guaranteed to come from that same row — so a plain GROUP BY would actually work here too. But that guarantee is SQLite-specific, not standard SQL, and it silently breaks the moment a second aggregate gets added. ROW_NUMBER() OVER (...) = 1 is the Day 04 pattern that works the same way on MySQL, so that's what this notebook uses throughout.

Views compound

Q16 joins this pattern's teams-side view through two more tables (team_league_lookup → League) without repeating any of the window-function logic — that's the entire point of defining it once.
