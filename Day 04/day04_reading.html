String Functions, Subqueries, CTEs, Temp Tables & Views

Cleaning and reshaping text, then four different ways to reuse a query's result: nested, named, materialized, or saved.

What you'll be able to do after this lesson

  • Trim, slice, and rebuild text with LTRIM/RTRIM/TRIM, LEFT/RIGHT/SUBSTRING/LOCATE, CONCAT, REPLACE, LOWER/UPPER/LENGTH.
  • Fill in gaps left by a CASE expression with COALESCE/IFNULL.
  • Write a scalar subquery (one value) and a row subquery (a tuple, matched with IN).
  • Use a subquery as a derived table in FROM, then rewrite the same idea more readably with a CTE.
  • Chain multiple CTEs together, and know when to reach for a temporary table or a view instead.
  • Choose the right tool — subquery, CTE, temp table, or view — for a given reuse scenario.

1Trimming whitespace

Real data is rarely clean — exports and manual entry leave stray spaces around text.

FunctionRemoves
LTRIM(str)Leading (left-side) spaces only.
RTRIM(str)Trailing (right-side) spaces only.
TRIM(str)Both sides at once.

Business question: a CSV export from a legacy CRM padded every point-of-contact name with stray spaces — clean it up before the data gets loaded anywhere else.

day04_string_functions_subqueries_ctes.sql
SELECT LTRIM(' Alexander Freberg') AS left_trim; SELECT RTRIM('Alexander Freberg ') AS right_trim; SELECT TRIM(' Alexander Freberg ') AS trim_both;
Only whitespace, by default

Plain TRIM(str) strips spaces. MySQL's fuller form, TRIM(BOTH '.' FROM str), trims a specific character instead — rarely needed, but good to know it exists.

2Extracting parts of a string

LEFT/RIGHT grab a fixed number of characters from either end; SUBSTRING grabs a slice from any starting position; LOCATE finds where a character sits so the other three don't have to hardcode a position.

Business question: marketing wants a 4-letter account-code abbreviation for a print report, and a data-quality check that every account's website follows the expected www.company.com pattern.

day04_string_functions_subqueries_ctes.sql
SELECT name, LEFT(name, 4) AS account_code FROM accounts; -- SUBSTRING(str, start, length) — 1-indexed, same indexing LOCATE returns -- every website looks like 'www.walmart.com' — this pulls out everything before the FIRST dot SELECT website, SUBSTRING(website, 1, LOCATE('.', website) - 1) AS website_prefix FROM accounts; SELECT primary_poc, LOCATE(' ', primary_poc) AS space_position FROM accounts;
LOCATE is 1-indexed, and 0 means "not found"

Unlike most programming languages, position 1 is the first character — and if the search string never appears, LOCATE returns 0, not -1 or NULL.

Finds the FIRST match only

website has two dots (www.walmart.com) — LOCATE('.', website) stops at the first one, so this extracts 'www', not the company name. Getting the middle segment would need a second LOCATE starting after the first match — not needed for today's lesson, but worth knowing the limit.

The -1 in this example

LOCATE('.', website) - 1 is the length of everything before the dot — feeding that as the length argument to SUBSTRING is how Section 3's email-builder finds a name split too.

3Building and cleaning strings

CONCAT glues pieces together; REPLACE swaps every occurrence of one substring for another; LOWER/ UPPER normalize case; LENGTH counts characters.

Business question: sales wants a company email address auto-generated for every point of contact — firstname.lastname@accountname.com, all lowercase, no spaces.

day04_string_functions_subqueries_ctes.sql
WITH name_split AS ( SELECT REPLACE(name, ' ', '') AS clean_account_name, LEFT(primary_poc, LOCATE(' ', primary_poc) - 1) AS first_name, RIGHT(primary_poc, LENGTH(primary_poc) - LOCATE(' ', primary_poc)) AS last_name FROM accounts ) SELECT first_name, last_name, CONCAT(LOWER(first_name), '.', LOWER(last_name), '@', LOWER(clean_account_name), '.com') AS email FROM name_split;
Don't worry about WITH yet

This is a CTE (Section 8 covers the syntax) — it's used here only so the first/last-name split doesn't have to be repeated three times inside one long SELECT.

Each piece is one function, chained

LEFT + LOCATE gets the first name, RIGHT + LENGTH + LOCATE gets the last name, REPLACE strips spaces from the account name — then CONCAT stitches all of it together.

4COALESCE / IFNULL — filling in the gaps

A CASE that doesn't cover every possibility leaves some rows NULL (Day 03 covered this with ELSE). IFNULL(expr, fallback) swaps in a fallback value wherever expr is NULL — a lighter-weight fix than adding another WHEN. COALESCE does the same thing but accepts any number of arguments, returning the first one that isn't NULL — IFNULL is really just MySQL's two-argument shortcut for it.

Business question: bucket every order by item count, but the defined buckets only cover 0–100 and 101–200 — anything bigger needs to read "200+" instead of a blank cell on the dashboard.

day04_string_functions_subqueries_ctes.sql
WITH total_range AS ( SELECT CASE WHEN total BETWEEN 0 AND 100 THEN '0-100' WHEN total BETWEEN 101 AND 200 THEN '101-200' END AS total_range FROM orders ) SELECT IFNULL(total_range, '200+') AS total_range FROM total_range;
No ELSE means NULL, on purpose

Leaving the CASE without an ELSE is what creates the gap IFNULL then fills — the two techniques are meant to pair together, not compete.

Halfway point

Sections 1–4 covered text. From here on, every section is about reusing a query's result — first stuffed inline as a subquery, then named, then saved outright.

5Scalar subqueries

A subquery is a query nested inside another one. A scalar subquery is the simplest kind — it returns exactly one row, one column, one value — so it can be used anywhere a single literal value could go, like the right-hand side of = or >.

Business question: leadership wants total sales for the single most recent day orders were placed, and finance wants every order that sold for more than the company-wide average.

day04_string_functions_subqueries_ctes.sql
-- hardcoding the date works once, but breaks the moment new orders arrive SELECT SUM(total_amt_usd) AS total_sales FROM orders WHERE DATE(occurred_at) = '2017-01-02'; -- a scalar subquery keeps it correct automatically, no matter when this runs SELECT SUM(total_amt_usd) AS total_sales FROM orders WHERE DATE(occurred_at) = (SELECT MAX(DATE(occurred_at)) FROM orders); SELECT * FROM orders WHERE total_amt_usd > (SELECT AVG(total_amt_usd) FROM orders);
Self-maintaining, not just shorter

The hardcoded-date version silently goes stale as soon as newer orders arrive — the subquery version always reflects the current data.

Must return exactly one value

If a subquery used with = or > ever returns more than one row, MySQL raises an error at runtime — this is exactly what Section 6's row subquery is for.

6Row subqueries — matching a tuple

When "one value" isn't enough to identify the right row — like needing both an account and its latest timestamp together — compare a tuple of columns against a subquery that returns matching tuples, using IN.

Business question: the web team wants each account's single most recent web event.

day04_string_functions_subqueries_ctes.sql
SELECT account_id, occurred_at, channel FROM web_events WHERE (account_id, occurred_at) IN ( SELECT account_id, MAX(occurred_at) FROM web_events GROUP BY account_id ) ORDER BY account_id;
Why not just MAX(occurred_at) alone

MAX(occurred_at) by itself returns one timestamp — the single latest event across the whole table. Pairing it with account_id in GROUP BY, then matching both columns as a tuple, is what makes this "latest PER account" instead.

The subquery here returns many rows

Unlike Section 5, this subquery returns one row per account — that's fine, because IN (unlike =) accepts a list of matches, not just one.

7Derived tables — a subquery in FROM

A subquery isn't limited to WHERE — placed in FROM and given an alias, it stands in for a real table, letting the outer query aggregate a result that's already aggregated once.

Business question: marketing wants the average number of daily web events per channel — that needs two passes of aggregation: events per day per channel first, then the average of those daily counts.

day04_string_functions_subqueries_ctes.sql
-- pass 1: events per day, per channel SELECT channel, DATE(occurred_at) AS day, COUNT(*) AS events FROM web_events GROUP BY day, channel; -- pass 2: average those daily counts, per channel — the derived table is the FROM subquery SELECT channel, AVG(events) AS avg_events_per_day FROM ( SELECT channel, DATE(occurred_at) AS day, COUNT(*) AS events FROM web_events GROUP BY day, channel ) AS daily_channel_events GROUP BY channel;
A derived table needs an alias

AS daily_channel_events is mandatory here — MySQL rejects an unaliased subquery in FROM, since the outer query needs a name to reference its columns by.

You can't SELECT AVG(events) directly from the first query

events is itself the output of an aggregate (COUNT(*)) — SQL won't let you aggregate an aggregate in the same SELECT, which is exactly why this needs two nested passes.

8CTEs — WITH ... AS

skeleton
WITH <cte_name> AS ( <query> ) SELECT ... FROM <cte_name>;

A Common Table Expression is the same idea as Section 7's derived table — a named, temporary result set — but declared up front with WITH instead of buried inside FROM. Once declared, a CTE reads like a real table for the rest of the statement.

Business question: re-solve Section 7's channel-average question more readably, and separately, find Parch & Posey's single highest lifetime-spend customer.

day04_string_functions_subqueries_ctes.sql
WITH daily_channel_events AS ( SELECT DATE(occurred_at) AS day, channel, COUNT(*) AS events FROM web_events GROUP BY day, channel ) SELECT channel, AVG(events) AS avg_events_per_day FROM daily_channel_events GROUP BY channel; WITH top_customer AS ( SELECT a.id, a.name, SUM(o.total_amt_usd) AS total_sales FROM orders o JOIN accounts a ON o.account_id = a.id GROUP BY a.id, a.name ORDER BY total_sales DESC LIMIT 1 ) SELECT * FROM top_customer;
Same result, more readable

Compare this to Section 7's version — the query structure is identical, but the CTE names the intermediate step before it's used instead of making the reader find it nested inside FROM.

A CTE only lives for one statement

Once the final SELECT finishes, top_customer is gone — the very next query can't reference it. That limitation is exactly what Sections 10–11 solve.

9Chained CTEs

One CTE can reference an earlier CTE defined in the same WITH clause — separated by a comma — letting you build a multi-step calculation as a readable sequence instead of one deeply nested query.

Business question: for that same top customer, how many web events came through each channel — and separately, is any account's total spend above the company-wide average account spend?

day04_string_functions_subqueries_ctes.sql
WITH top_customer AS ( SELECT a.id, a.name, SUM(o.total_amt_usd) AS total_sales FROM orders o JOIN accounts a ON o.account_id = a.id GROUP BY a.id, a.name ORDER BY total_sales DESC LIMIT 1 ) SELECT a.name, w.channel, COUNT(*) AS num_events FROM accounts a JOIN web_events w ON a.id = w.account_id JOIN top_customer ON a.id = top_customer.id GROUP BY a.name, w.channel ORDER BY num_events DESC; -- a second CTE, chained off the first with a comma WITH account_totals AS ( SELECT a.id, a.name, SUM(o.total_amt_usd) AS total_spend FROM orders o JOIN accounts a ON o.account_id = a.id GROUP BY a.id, a.name ), avg_total AS ( SELECT AVG(total_spend) AS avg_total_spend FROM account_totals ) SELECT * FROM account_totals WHERE total_spend > (SELECT avg_total_spend FROM avg_total);
top_customer joined like a real table

Once declared, a CTE is joined exactly like accounts or orders — no special syntax needed to bring it into the rest of the query.

Order matters in the chain

avg_total references account_totals, so account_totals must be declared first — a CTE can only see CTEs that came before it, not after.

10Temporary tables

skeleton
CREATE TEMPORARY TABLE <table_name> <query>; -- now query it like any other table, across as many separate statements as needed SELECT * FROM <table_name>;

A CTE disappears the moment its statement finishes. A temporary table solves that by actually materializing the result — it persists for the rest of the session (until you disconnect, or run DROP TEMPORARY TABLE), so multiple separate queries can reuse it without recomputing anything.

Business question: the same top-customer question as Section 9, but the sales team wants to run several different follow-up queries against it during one working session, not just one.

day04_string_functions_subqueries_ctes.sql
CREATE TEMPORARY TABLE top_customer SELECT a.id, a.name, SUM(o.total_amt_usd) AS total_sales FROM orders o JOIN accounts a ON o.account_id = a.id GROUP BY a.id, a.name ORDER BY total_sales DESC LIMIT 1; -- statement 1, later in the same session SELECT * FROM top_customer; -- statement 2, also later, no recomputation needed SELECT a.name, w.channel, COUNT(*) AS num_events FROM accounts a JOIN web_events w ON a.id = w.account_id JOIN top_customer ON a.id = top_customer.id GROUP BY a.name, w.channel ORDER BY num_events DESC;
Materialized, not just named

Unlike a CTE, this actually writes rows to a real (temporary) table on disk/memory — that's what lets it survive past one statement, at the cost of the storage and write time a CTE doesn't need.

Session-scoped, not shared

Only the connection that created it can see it — another user, or a new connection from the same client, gets "table doesn't exist" if they try to query it.

11Views

skeleton
CREATE VIEW <view_name> AS <query>; -- query it like any other table, from any session, indefinitely SELECT * FROM <view_name>;

A view looks like a temporary table's syntax, but is permanent and shared: MySQL saves the query itself, not its result, so every time the view is queried it re-runs against current data — and unlike a temp table, any session that can see the database can see the view.

Business question: sales wants a "top 10 customers" leaderboard they can query repeatedly, from any session, without anyone re-writing the ranking logic each time.

day04_string_functions_subqueries_ctes.sql
CREATE VIEW top10_customers AS SELECT a.id, a.name, SUM(o.total_amt_usd) AS total_sales FROM orders o JOIN accounts a ON o.account_id = a.id GROUP BY a.id, a.name ORDER BY total_sales DESC LIMIT 10; SELECT * FROM top10_customers; -- behaves exactly like a table in any query — join straight to it SELECT w.channel, COUNT(*) AS num_events FROM web_events w JOIN top10_customers t ON w.account_id = t.id GROUP BY w.channel ORDER BY num_events DESC;
Always current, never stale

Because a view re-runs its underlying query on every access, it never needs refreshing the way a temp table's snapshot would — if orders changes, the view's next query reflects that immediately.

No physical storage of the data itself

The tradeoff for always being current: a view does the full underlying computation every time it's queried, unlike a temp table's one-time materialization.

12Choosing between them

All four techniques answer the same underlying need — reuse an intermediate result — with different tradeoffs on lifetime, visibility, and whether the data is actually stored.

FeatureSubqueryCTETemp TableView
Scope & lifetimeInside its enclosing query onlyOne statement onlyRest of the session, or until droppedUntil dropped — permanent
Visible to other sessions?N/AN/ANoYes
Reusable across multiple queries?No — rewrite it each timeOnly within the one statement that declares itYes, any query in the sessionYes, any query, any session
Data actually stored?No — recomputed every referenceNo — recomputed every referenceYes — materialized onceNo — query re-runs every time
Supports INSERT/UPDATE/DELETE?Generally noGenerally noYesGenerally no
Best forA one-off comparison or filterReadability — naming a step before it's usedSeveral follow-up queries reusing one expensive resultA saved, shareable definition everyone should query the same way

Reach for a subquery when...

The intermediate result is used exactly once, inline, and naming it separately would be more ceremony than it's worth.

Reach for a CTE when...

The query has multiple steps and naming each one makes the whole statement easier to read — the default choice for most multi-step queries today.

Reach for a temp table when...

You'll run several different follow-up queries against the same expensive intermediate result, within one working session.

Reach for a view when...

Other people, other sessions, or other tools (a BI dashboard, a report) need to query the exact same logic without re-deriving it.
