Subqueries, CTEs & Views

Four ways to reuse a query's result — nested, named, materialized, or saved.

What you'll be able to do after this lesson

  • Write a scalar subquery (one value) and a row subquery (a tuple, matched with IN).
  • Use a subquery as a derived table in FROM, then rewrite the same idea more readably with a CTE.
  • Chain multiple CTEs together, and know when to reach for a temporary table or a view instead.
  • Choose the right tool — subquery, CTE, temp table, or view — for a given reuse scenario.
Before you start

Still the same rawaj database from Days 01–03 — run Databases/rawaj_db.sql first if you haven't already, then USE rawaj;. No new setup script today.

1Scalar subqueries

A subquery is a query nested inside another one. A scalar subquery is the simplest kind — it returns exactly one row, one column, one value — so it can be used anywhere a single literal value could go, like the right-hand side of = or >.

Business question: leadership wants total sales for the single most recent day orders were placed, and finance wants every order that sold for more than the company-wide average.

day04_subqueries_ctes_and_views.sql
-- hardcoding the date works once, but breaks the moment new orders arrive SELECT SUM(total_amount) AS total_sales FROM orders WHERE DATE(order_date) = '2024-03-18'; -- a scalar subquery keeps it correct automatically, no matter when this runs SELECT SUM(total_amount) AS total_sales FROM orders WHERE DATE(order_date) = (SELECT MAX(DATE(order_date)) FROM orders); SELECT * FROM orders WHERE total_amount > (SELECT AVG(total_amount) FROM orders);
Self-maintaining, not just shorter

The hardcoded-date version silently goes stale as soon as newer orders arrive — the subquery version always reflects the current data.

Must return exactly one value

If a subquery used with = or > ever returns more than one row, MySQL raises an error at runtime — this is exactly what Section 2's row subquery is for.

2Row subqueries — matching a tuple

When "one value" isn't enough to identify the right row — like needing both a customer and its latest timestamp together — compare a tuple of columns against a subquery that returns matching tuples, using IN.

Business question: the web team wants each customer's single most recent web event.

day04_subqueries_ctes_and_views.sql
SELECT customer_id, occurred_at, channel FROM web_events WHERE (customer_id, occurred_at) IN ( SELECT customer_id, MAX(occurred_at) FROM web_events GROUP BY customer_id ) ORDER BY customer_id;
Why not just MAX(occurred_at) alone

MAX(occurred_at) by itself returns one timestamp — the single latest event across the whole table. Pairing it with customer_id in GROUP BY, then matching both columns as a tuple, is what makes this "latest PER customer" instead.

The subquery here returns many rows

Unlike Section 1, this subquery returns one row per customer — that's fine, because IN (unlike =) accepts a list of matches, not just one.

3Derived tables — a subquery in FROM

A subquery isn't limited to WHERE — placed in FROM and given an alias, it stands in for a real table, letting the outer query aggregate a result that's already aggregated once.

Business question: marketing wants the average number of daily web events per channel — that needs two passes of aggregation: events per day per channel first, then the average of those daily counts.

day04_subqueries_ctes_and_views.sql
-- pass 1: events per day, per channel SELECT channel, DATE(occurred_at) AS day, COUNT(*) AS events FROM web_events GROUP BY day, channel; -- pass 2: average those daily counts, per channel — the derived table is the FROM subquery SELECT channel, AVG(events) AS avg_events_per_day FROM ( SELECT channel, DATE(occurred_at) AS day, COUNT(*) AS events FROM web_events GROUP BY day, channel ) AS daily_channel_events GROUP BY channel;
A derived table needs an alias

AS daily_channel_events is mandatory here — MySQL rejects an unaliased subquery in FROM, since the outer query needs a name to reference its columns by.

You can't SELECT AVG(events) directly from the first query

events is itself the output of an aggregate (COUNT(*)) — SQL won't let you aggregate an aggregate in the same SELECT, which is exactly why this needs two nested passes.

4CTEs — WITH ... AS

skeleton
WITH <cte_name> AS ( <query> ) SELECT ... FROM <cte_name>;

A Common Table Expression is the same idea as Section 3's derived table — a named, temporary result set — but declared up front with WITH instead of buried inside FROM. Once declared, a CTE reads like a real table for the rest of the statement. Day 03 already previewed this syntax briefly for a string-building example — this section covers it properly.

Business question: re-solve Section 3's channel-average question more readably, and separately, find Rawaj's single highest lifetime-spend customer.

day04_subqueries_ctes_and_views.sql
WITH daily_channel_events AS ( SELECT DATE(occurred_at) AS day, channel, COUNT(*) AS events FROM web_events GROUP BY day, channel ) SELECT channel, AVG(events) AS avg_events_per_day FROM daily_channel_events GROUP BY channel; WITH top_customer AS ( SELECT c.customer_id, c.first_name, c.last_name, SUM(o.total_amount) AS total_sales FROM orders o JOIN customers c ON o.customer_id = c.customer_id GROUP BY c.customer_id, c.first_name, c.last_name ORDER BY total_sales DESC LIMIT 1 ) SELECT * FROM top_customer;
Same result, more readable

Compare this to Section 3's version — the query structure is identical, but the CTE names the intermediate step before it's used instead of making the reader find it nested inside FROM.

A CTE only lives for one statement

Once the final SELECT finishes, top_customer is gone — the very next query can't reference it. That limitation is exactly what Sections 6–7 solve.

5Chained CTEs

One CTE can reference an earlier CTE defined in the same WITH clause — separated by a comma — letting you build a multi-step calculation as a readable sequence instead of one deeply nested query.

Business question: for that same top customer, how many web events came through each channel — and separately, is any customer's total spend above the company-wide average customer spend?

day04_subqueries_ctes_and_views.sql
WITH top_customer AS ( SELECT c.customer_id, c.first_name, c.last_name, SUM(o.total_amount) AS total_sales FROM orders o JOIN customers c ON o.customer_id = c.customer_id GROUP BY c.customer_id, c.first_name, c.last_name ORDER BY total_sales DESC LIMIT 1 ) SELECT c.first_name, c.last_name, w.channel, COUNT(*) AS num_events FROM customers c JOIN web_events w ON c.customer_id = w.customer_id JOIN top_customer ON c.customer_id = top_customer.customer_id GROUP BY c.first_name, c.last_name, w.channel ORDER BY num_events DESC; -- a second CTE, chained off the first with a comma WITH customer_totals AS ( SELECT c.customer_id, c.first_name, c.last_name, SUM(o.total_amount) AS total_spend FROM orders o JOIN customers c ON o.customer_id = c.customer_id GROUP BY c.customer_id, c.first_name, c.last_name ), avg_total AS ( SELECT AVG(total_spend) AS avg_total_spend FROM customer_totals ) SELECT * FROM customer_totals WHERE total_spend > (SELECT avg_total_spend FROM avg_total);
top_customer joined like a real table

Once declared, a CTE is joined exactly like customers or orders — no special syntax needed to bring it into the rest of the query.

Order matters in the chain

avg_total references customer_totals, so customer_totals must be declared first — a CTE can only see CTEs that came before it, not after.

6Temporary tables

skeleton
CREATE TEMPORARY TABLE <table_name> <query>; -- now query it like any other table, across as many separate statements as needed SELECT * FROM <table_name>;

A CTE disappears the moment its statement finishes. A temporary table solves that by actually materializing the result — it persists for the rest of the session (until you disconnect, or run DROP TEMPORARY TABLE), so multiple separate queries can reuse it without recomputing anything.

Business question: the same top-customer question as Section 5, but the sales team wants to run several different follow-up queries against it during one working session, not just one.

day04_subqueries_ctes_and_views.sql
CREATE TEMPORARY TABLE top_customer SELECT c.customer_id, c.first_name, c.last_name, SUM(o.total_amount) AS total_sales FROM orders o JOIN customers c ON o.customer_id = c.customer_id GROUP BY c.customer_id, c.first_name, c.last_name ORDER BY total_sales DESC LIMIT 1; -- statement 1, later in the same session SELECT * FROM top_customer; -- statement 2, also later, no recomputation needed SELECT c.first_name, c.last_name, w.channel, COUNT(*) AS num_events FROM customers c JOIN web_events w ON c.customer_id = w.customer_id JOIN top_customer ON c.customer_id = top_customer.customer_id GROUP BY c.first_name, c.last_name, w.channel ORDER BY num_events DESC;
Materialized, not just named

Unlike a CTE, this actually writes rows to a real (temporary) table on disk/memory — that's what lets it survive past one statement, at the cost of the storage and write time a CTE doesn't need.

Session-scoped, not shared

Only the connection that created it can see it — another user, or a new connection from the same client, gets "table doesn't exist" if they try to query it.

7Views

skeleton
CREATE VIEW <view_name> AS <query>; -- query it like any other table, from any session, indefinitely SELECT * FROM <view_name>;

A view looks like a temporary table's syntax, but is permanent and shared: MySQL saves the query itself, not its result, so every time the view is queried it re-runs against current data — and unlike a temp table, any session that can see the database can see the view.

Business question: sales wants a "top 10 customers" leaderboard they can query repeatedly, from any session, without anyone re-writing the ranking logic each time.

day04_subqueries_ctes_and_views.sql
CREATE VIEW top10_customers AS SELECT c.customer_id, c.first_name, c.last_name, SUM(o.total_amount) AS total_sales FROM orders o JOIN customers c ON o.customer_id = c.customer_id GROUP BY c.customer_id, c.first_name, c.last_name ORDER BY total_sales DESC LIMIT 10; SELECT * FROM top10_customers; -- behaves exactly like a table in any query — join straight to it SELECT w.channel, COUNT(*) AS num_events FROM web_events w JOIN top10_customers t ON w.customer_id = t.customer_id GROUP BY w.channel ORDER BY num_events DESC;
Always current, never stale

Because a view re-runs its underlying query on every access, it never needs refreshing the way a temp table's snapshot would — if orders changes, the view's next query reflects that immediately.

No physical storage of the data itself

The tradeoff for always being current: a view does the full underlying computation every time it's queried, unlike a temp table's one-time materialization.

8Choosing between them

All four techniques answer the same underlying need — reuse an intermediate result — with different tradeoffs on lifetime, visibility, and whether the data is actually stored.

FeatureSubqueryCTETemp TableView
Scope & lifetimeInside its enclosing query onlyOne statement onlyRest of the session, or until droppedUntil dropped — permanent
Visible to other sessions?N/AN/ANoYes
Reusable across multiple queries?No — rewrite it each timeOnly within the one statement that declares itYes, any query in the sessionYes, any query, any session
Data actually stored?No — recomputed every referenceNo — recomputed every referenceYes — materialized onceNo — query re-runs every time
Supports INSERT/UPDATE/DELETE?Generally noGenerally noYesGenerally no
Best forA one-off comparison or filterReadability — naming a step before it's usedSeveral follow-up queries reusing one expensive resultA saved, shareable definition everyone should query the same way

Reach for a subquery when...

The intermediate result is used exactly once, inline, and naming it separately would be more ceremony than it's worth.

Reach for a CTE when...

The query has multiple steps and naming each one makes the whole statement easier to read — the default choice for most multi-step queries today.

Reach for a temp table when...

You'll run several different follow-up queries against the same expensive intermediate result, within one working session.

Reach for a view when...

Other people, other sessions, or other tools (a BI dashboard, a report) need to query the exact same logic without re-deriving it.
