1The cursor — what every database call reduces to

Before reaching for any convenience layer, it's worth seeing the raw pattern once: a connection to the database, a cursor to run statements through, execute() to run a query, and fetchall()/ fetchone() to pull the results back. Every tool in this lesson — pandas, SQLAlchemy, jupysql's %%sql — is built on exactly this, for any database driver.

day06_python_mysql.ipynb
import os from dotenv import load_dotenv import mysql.connector load_dotenv() # reads DB_PASSWORD from the local .env file raw_conn = mysql.connector.connect( host="localhost", port=3306, user="root", password=os.getenv("DB_PASSWORD"), database="rawaj", use_pure=True, ) cursor = raw_conn.cursor() cursor.execute("SELECT governorate_name FROM governorates ORDER BY governorate_name") for row in cursor.fetchall(): print(row) cursor.close() raw_conn.close()
Plain tuples, not a DataFrame

fetchall() returns a list of plain tuples — no column names, no formatting. That gap is exactly what pandas and jupysql fill next.

Tied to one driver

This exact code only works with mysql-connector-python. SQLAlchemy's whole purpose (Section 2) is giving you the same interface regardless of which driver or engine is underneath.

2Connecting Python to MySQL with SQLAlchemy

create_engine(...) is the standard way to open a database connection from Python — one function, and the connection string's prefix is the only thing that changes between database engines.

Business question: credentials need to live somewhere real code can read them, without ever being typed into a notebook or committed to git.

day06_python_mysql.ipynb
import os from dotenv import load_dotenv from sqlalchemy import create_engine, text from sqlalchemy.engine import URL import pandas as pd load_dotenv() # reads DB_PASSWORD from the local .env file mysql_url = URL.create( "mysql+mysqlconnector", username="root", password=os.getenv("DB_PASSWORD"), host="localhost", port=3306, database="rawaj", ) mysql_engine = create_engine(mysql_url, connect_args={"use_pure": True})
.env is never committed

.env is listed in .gitignore — only .env.example (a template with no real values) is tracked in git. Copy it, fill in your own credentials, keep the real file local.

URL.create(...), not an f-string

Hand-building the connection string with an f-string breaks the moment a password contains @, :, /, or % — an @ inside the password gets misread as the separator before the hostname, producing a confusing "unknown host" error that has nothing to do with the actual host. URL.create() percent-encodes every part correctly, regardless of what characters it contains.

use_pure — see the callout in Section 5

Forces the pure-Python driver instead of the C extension, avoiding a "commands out of sync" bug the C extension has with stored procedures that return a result set.

3jupysql — running SQL cells directly in a notebook

jupysql (the actively-maintained successor to the older ipython-sql) adds %sql (one line) and %%sql (a whole cell) magics — write real SQL directly in a notebook cell instead of wrapping every query in pd.read_sql(text("..."), engine).

Business question: re-run a familiar Day 03 JOIN straight from the notebook, to confirm the connection actually works end to end.

day06_python_mysql.ipynb
%load_ext sql %sql mysql_engine --alias mysql # bind jupysql to an existing SQLAlchemy engine %%sql SELECT CONCAT(c.first_name, ' ', c.last_name) AS customer_name, SUM(o.total_amount) AS total_sales FROM orders o JOIN customers c ON o.customer_id = c.customer_id GROUP BY c.customer_id, c.first_name, c.last_name ORDER BY total_sales DESC LIMIT 5;
Passing an engine variable is the cleanest pattern

%sql mysql_engine reuses the exact same engine the rest of your Python code (like pd.read_sql) already uses — no second, separate connection string to keep in sync.

Nothing new syntactically

Same JOIN technique from Day 03 — the point of this quick check is proving the plumbing works, not teaching new SQL. The full sweep through every technique happens in day06_python_sqlite.ipynb, below.

This notebook is a short connection check

day06_python_mysql.ipynb is just enough to prove the Python↔MySQL plumbing works — one JOIN, then the stored-procedure calls in Section 5. Day 07's project runs on SQLite, not MySQL, so most of Day 06's actual depth is in day06_python_sqlite.ipynb: a full sweep through every Day 01–05 concept — LIMIT/OFFSET, WHERE, every JOIN variant, CASE, string functions, subqueries, CTEs, temp tables, views, every window function, all re-run via %%sql against the migrated copy.

4Passing parameters safely

Every query so far has had its filter values hardcoded. Real code usually takes that value from somewhere else — a form field, a function argument, another system — and the way you get it into the query matters. This is covered hands-on in day06_python_sqlite.ipynb, since SQLite is where the rest of this course's Python work happens.

Business question: build a small function, orders_for_customer(customer_id), that a dashboard could call with whatever customer a user picks. (This uses sqlite_conn — the SQLite connection from Section 7 below — since that's the connection this course's Python work uses from here on.)

The wrong way — an f-string

def orders_for_customer_UNSAFE(customer_id):
    query = f"SELECT ... WHERE customer_id = {customer_id}"
    return pd.read_sql(query, sqlite_conn)

The right way — a bound parameter

def orders_for_customer(customer_id):
    query = "SELECT ... WHERE customer_id = :cust_id"
    return pd.read_sql(query, sqlite_conn, params={"cust_id": customer_id})
What actually happens with a malicious input

Call the f-string version with customer_id = "1 OR 1=1" and it returns every order in the table — classic SQL injection, since the value was pasted directly into the query text and then parsed as SQL. Call the bound-parameter version with the exact same input and it comes back safe: SQLite is strict about comparing text to an integer column, so the malicious string simply matches nothing and the query returns zero rows (see it run in day06_python_sqlite.ipynb). MySQL's driver would instead coerce the string down to the number it starts with (1) and return that customer's normal rows — a different failure mode, but the value still never gets a chance to be parsed as SQL, which is the only guarantee that actually matters.

The single most important habit in this notebook: never build a query string with f-strings/.format()/%-formatting using a value that came from outside your own code. Always use a placeholder (:name with SQLAlchemy, %s with a raw DBAPI cursor) and pass the value separately.

5Calling stored procedures from Python

Day 05's stored procedures needed DELIMITER because the mysql CLI splits a script into statements on every semicolon. A Python driver sends the whole procedure body as one request — no DELIMITER needed at all from here on.

day06_python_mysql.ipynb
%%sql CALL customer_sales_report(1); %%sql CALL get_total_revenue(@rev); %%sql SELECT @rev AS total_revenue;
Two driver quirks worth knowing

mysql-connector-python ships two implementations: a fast C extension (the default) and a pure-Python fallback. The C extension has a known bug calling a stored procedure that returns a result set — it leaves the connection in a broken "commands out of sync" state for whatever query runs next. Section 2's connect_args={"use_pure": True} avoids this entirely.

Separately, calling a result-returning procedure (customer_sales_report) right before an OUT-parameter one (get_total_revenue) can silently leave @rev empty, even with use_pure — the driver gets confused switching between the two call styles. mysql_engine.dispose() (closes every pooled connection so the next query starts fresh) right before calling get_total_revenue is the fix — see it in day06_python_mysql.ipynb.

6Loading results into pandas

pd.read_sql(query, engine) is the bridge between a SQL result and everything pandas can do with it — the DataFrame that comes back behaves exactly like data loaded any other way, so every pandas method (.plot(), .describe(), .to_csv()) works the same. On a SQLAlchemy engine, wrap the query string in text(...) — that's the habit that keeps working once you move from read_sql to connection.execute(), which requires it. Section 10 below puts this to work on the charts finance and marketing actually asked for.

7Migrating to SQLite with pandas

Day 07's project runs against a local .sqlite file instead of a MySQL server. day06_python_sqlite.ipynb first rebuilds the already-familiar rawaj as a local SQLite file — a real, useful skill on its own (migrating between engines), and a gentler way to meet the SQLite connection pattern than jumping straight into Day 07's unfamiliar schema.

Business question: a teammate without MySQL installed still needs to work with this data — hand them a single portable file instead.

day06_python_sqlite.ipynb
import sqlite3 sqlite_conn = sqlite3.connect("../Databases/rawaj.sqlite") for table in ["governorates", "account_managers", "sellers", "customers", "orders", "web_events", "reviews"]: df = pd.read_sql(text(f"SELECT * FROM {table}"), mysql_engine) df.to_sql(table, sqlite_conn, index=False, if_exists="replace") sqlite_conn.commit()
No SQLAlchemy on the destination side

sqlite3 is a Python stdlib module — nothing to install. df.to_sql accepts a raw sqlite3.Connection just as happily as a SQLAlchemy engine; the source side (mysql_engine) still needs SQLAlchemy, for the reasons in Section 2.

Read from one engine, write to another

pd.read_sql and df.to_sql don't care what's on either end — a DataFrame is the universal middle step.

Generated, not committed

This file is regenerated by running the notebook, not stored in git — same reasoning as never committing .env: it's derived, disposable local state.

Seven tables, not all fourteen

This list covers what today's exercises need — the rest of Rawaj's schema (products, sellers' listings, order line items, and the rest) isn't part of this local copy. Querying one of those tables against rawaj.sqlite fails with "no such table"; the MySQL rawaj database still has all 14.

A migration changes types, not just location

Round-tripping through a DataFrame preserves every row, but not every column's original type. governorates.manager_id has a NULL for the one governorate with no manager yet — pandas responds by widening that whole integer column to a float, so it prints as 5.0 instead of 5 once it's back out of SQLite. Every DECIMAL column becomes a plain floating-point number the same way, which is why a total that was exactly 60579.87 in MySQL can print as 60579.869999999995 here — a floating-point rounding artifact, not a data error. Verifying a migration with COUNT(*) alone won't catch this; comparing a SUM() on both sides would.

8The cursor, once more, on SQLite

Same DB-API pattern from Section 1, different driver underneath — and this time, no new connection needed: sqlite_conn from the migration step above already is a connection.

day06_python_sqlite.ipynb
cursor = sqlite_conn.cursor() cursor.execute("SELECT governorate_name FROM governorates ORDER BY governorate_name") for row in cursor.fetchall(): print(row) cursor.close()

9Two ways to run %%sql against SQLite

No host, no username, no password — SQLite is just a single file the Python process opens directly. Everything else about querying it is identical to MySQL — including having a choice in how to connect.

Option 1 — through SQLAlchemy

sqlalchemy_demo_engine = create_engine(
    "sqlite:///../Databases/rawaj.sqlite"
)
%sql sqlalchemy_demo_engine --alias sqlite_via_sqlalchemy

Option 2 — jupysql directly, no SQLAlchemy

%sql sqlite:///../Databases/rawaj.sqlite --alias sqlite_rawaj

Both register a connection jupysql can run %%sql against, and both return identical results for the same query. Option 2 is what day06_python_sqlite.ipynb uses from here on — it's also the exact pattern Day 07's project notebook already uses, so getting comfortable with it now pays off directly later.

jupysql needs a connection string or an Engine — nothing less

It can't bind directly to a raw sqlite3.Connection the way pandas can. That's the one place SQLAlchemy genuinely earns its keep for SQLite — not for connecting in general, just for this specific magic.

10Visualizing results

SQL alone gets you a table. Python's real payoff is turning that table into something a stakeholder actually looks at.

Business question: sales leadership wants the daily revenue trend for their weekly review deck, not a table of numbers.

day06_python_sqlite.ipynb
daily_sales = pd.read_sql( "SELECT DATE(order_date) AS day, SUM(total_amount) AS daily_sales FROM orders GROUP BY day", sqlite_conn, ) daily_sales.plot(x="day", y="daily_sales", figsize=(10, 4), title="Daily Sales — rawaj")

The notebook does this two more times — total revenue by governorate as a bar chart for a quarterly review, and web-event channel mix as a pie chart for a marketing review — pulling straight from queries already in the sweep. Same idea every time: get a DataFrame, call .plot(), pick the chart shape that fits the question — a line for a trend over time, a bar for comparing categories, a pie for a proportional split.

11MySQL vs SQLite — what actually differs

Most of what you've learned transfers directly. A handful of functions don't exist in SQLite, or are spelled differently — worth recognizing before Day 07.

NeedMySQLSQLite
Format a dateDATE_FORMAT(col, '%Y-%m')STRFTIME('%Y-%m', col)
Difference between two datesDATEDIFF(d1, d2)No DATEDIFF — subtract JULIANDAY(d1) - JULIANDAY(d2) instead
Concatenate stringsCONCAT(a, b)a || b (SQLite 3.44+ also has a CONCAT() function, but || works on every version)
Auto-incrementing primary keyAUTO_INCREMENTAUTOINCREMENT
Stored proceduresCREATE PROCEDURENot supported at all — SQLite has no procedural logic
Everything else transfers directly

JOINs, CASE, subqueries, CTEs, and window functions (including RANK/LAG/LEAD) all work identically in SQLite — Day 07 leans on exactly these, just without stored procedures or MySQL's date-function names.

Python vocabulary from today

TermWhat it is
ConnectionOne open line to a specific database — created once, reused for many queries.
CursorRuns statements through a connection and hands back results, one query at a time.
Engine (SQLAlchemy)A reusable connection factory — one create_engine(...) call, shared by pd.read_sql, jupysql, and anything else that needs a connection.
Magic (%sql/%%sql)A Jupyter-only shortcut — jupysql intercepts the cell and runs it as SQL instead of Python.
DataFramepandas' table object — what pd.read_sql returns, and what every pandas method afterward operates on.
If something doesn't run

Access denied for user 'root'@'localhost' — check the password in .env against what actually unlocks MySQL Workbench/CLI for you. ModuleNotFoundError — run pip install -r requirements.txt from the repo root. Can't connect to MySQL server — the MySQL service isn't running; start it the same way you did for Days 01–05. UsageError: Line magic function `%sql` not found — the notebook was restarted; re-run the %load_ext sql cell. A relative path like ../Databases/rawaj.sqlite failing — Jupyter must be launched from inside the Day 06 folder, not the repo root.
