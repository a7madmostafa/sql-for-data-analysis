3WHERE — filtering rows

WHERE narrows which rows a query returns, evaluated before SELECT/ORDER BY/LIMIT get a chance to do anything — think of it as a gate that rows have to pass through first.

Business question: Finance wants to see every order worth more than 10,000 EGP — the company's biggest single sales, most valuable first.

day02_filtering_and_aggregation.sql
SELECT * FROM orders WHERE total_amount > 10000 ORDER BY total_amount DESC;
Comparison operators

=, >, <, >=, <= all work exactly as you'd expect from arithmetic.

Not-equal, three ways

!=, <> (standard SQL), and WHERE NOT customer_id = 1 all mean the same thing — != is the one you'll see most in practice.

4AND / OR — combining conditions

AND — narrows

Both conditions must hold. channel = 'facebook' AND customer_id = 631 returns only Facebook events, and only for that one customer — the smallest of the four possible result sets.

OR — widens

Either can hold. Swap in OR and you get every Facebook event from any customer, plus every event (any channel) from customer 631 — often a much bigger, looser result than intended.

Business question: did customer 631 specifically show up on Facebook — versus casting a much wider net for anything Facebook-related, plus everything from that customer regardless of channel?

day02_filtering_and_aggregation.sql
-- AND: narrow — only Facebook events from customer 631 SELECT * FROM web_events WHERE channel = 'facebook' AND customer_id = 631; -- OR: wide — Facebook events from anyone, plus every event from customer 631 SELECT * FROM web_events WHERE channel = 'facebook' OR customer_id = 631;
Same shape, different meaning

Only the keyword changed. AND returns customer 631's 3 Facebook events; OR returns 2,266 rows — every one of the 2,252 Facebook events sitewide, plus 631's own activity on every other channel too. The row counts these two return can differ by an order of magnitude, and MySQL never flags it — reading each condition back is the only defense.

The most common real-world SQL bug

Mixing up AND/OR is grammatically valid in exactly the same spot but changes the result drastically — and MySQL will never warn you, because both versions are perfectly correct SQL. The only defense is reading each condition back and asking "does this describe what I actually mean?"

5BETWEEN — range filtering

WHERE total_amount BETWEEN 2000 AND 4999 is shorthand for WHERE total_amount >= 2000 AND total_amount <= 4999 — both endpoints inclusive. It works on dates too — but on this schema, order_date isn't a plain date, it's a DATETIME, and that changes the endpoint math.

Business question: which orders fall in the 2,000–4,999 EGP mid-size range, and which orders came in during the final two days of 2024 plus New Year's Day, for a year-end cutoff report?

day02_filtering_and_aggregation.sql
-- numeric range SELECT order_id, total_amount FROM orders WHERE total_amount BETWEEN 2000 AND 4999; -- date range, done wrong: BETWEEN pads '2025-01-01' to 2025-01-01 00:00:00, -- so every Jan 1 order placed later that day is silently dropped SELECT order_id, order_date FROM orders WHERE order_date BETWEEN '2024-12-30' AND '2025-01-01'; -- done right: start at the first moment you want, stop before the first moment you don't SELECT order_id, order_date FROM orders WHERE order_date >= '2024-12-30' AND order_date < '2025-01-02';
Written out with AND/OR, this gets long fast

WHERE total_amount >= 2000 AND total_amount <= 4999 says exactly the same thing — BETWEEN is purely a shorter way to write a two-sided AND.

BETWEEN on a DATETIME column is a trap

BETWEEN really is inclusive of both endpoints — but a date literal like '2025-01-01' means midnight on that date, not the whole day. Against a DATETIME column, BETWEEN '2024-12-30' AND '2025-01-01' only matches orders placed at exactly 00:00:00 on Jan 1 — every other order that day is excluded, with no error to warn you. The fix is the pattern in the third query above: start the range at the first moment you want, and stop it before the first moment you don't (< 'day-after-the-last-day-you-want') — use this any time a reporting period ends on a real calendar day rather than a timestamp.

6IN vs OR

Business question: marketing wants every web event from Facebook, Instagram, or organic search — three channels at once.

day02_filtering_and_aggregation.sql
-- gets unwieldy fast SELECT * FROM web_events WHERE channel = 'facebook' OR channel = 'instagram' OR channel = 'organic'; -- identical result, one line SELECT * FROM web_events WHERE channel IN ('facebook', 'instagram', 'organic');
NOT IN works too

Excludes every value in the list instead of matching it — handy for "everything except these legacy channels."

7NULL checks

NULL means "no value was ever recorded here" — it is not 0, not an empty string '', and ordinary = silently fails to test for it (WHERE x = NULL matches nothing, with no error). Use IS NULL / IS NOT NULL instead.

Business question: Compliance wants a list of customers with no email on file, so outreach can flag them for a different contact method.

day02_filtering_and_aggregation.sql
SELECT customer_id, first_name, last_name FROM customers WHERE email IS NULL;
Rawaj actually has these

119 of Rawaj's 1,200 customers — about 1 in 10 — checked out as a guest and never left an email on file, so this query genuinely returns rows here, not a hypothetical. This is the everyday reason you reach for IS NULL: missing optional fields, unfilled form data, a join that didn't find a match (you'll see that scenario properly on Day 03).

8LIKE — pattern matching

Two wildcards: % matches any number of characters (including zero), _ matches exactly one.

PatternMatches
'A%'starts with A
'%a%'contains a, anywhere
'_a%''a' is the 2nd character
'_a___'exactly 5 characters, 'a' 2nd
'%ct'ends with 'ct'

Business question: marketing wants an alphabetized outreach list of every customer whose first name starts with A.

day02_filtering_and_aggregation.sql
SELECT first_name, last_name FROM customers WHERE first_name LIKE 'A%' ORDER BY first_name;
LIKE is case-insensitive by default in MySQL

'%el%' matches El-Sayed just as much as it matches Abdelrahman — MySQL's default collation doesn't distinguish upper from lowercase for text comparison. Searching last names for '%el%' returns 338 of Rawaj's 1,200 customers, not just the ones spelled with a capital El-. If you need a case-sensitive match, that's a separate, more advanced setting (a binary or case-sensitive collation) — worth knowing exists, not needed here.

9Aggregate functions beyond COUNT

Day 01 covered COUNT. Four more aggregate functions collapse a whole column into a single number the same way: SUM (total), AVG (average), MIN, and MAX. ROUND(value, n) rounds a number to n decimal places — useful the moment AVG returns something like 3848.321060.

Business question: leadership wants one summary row for a board slide — order count, smallest order, biggest order, average order, and total revenue, all at once.

day02_filtering_and_aggregation.sql
SELECT COUNT(*) AS OrderCount, MIN(total_amount) AS MinTotal, MAX(total_amount) AS MaxTotal, ROUND(AVG(total_amount), 2) AS AvgTotal, SUM(total_amount) AS TotalRevenue FROM orders;
One row, five numbers

Every aggregate here scans the same 6,000 rows independently — Rawaj's lifetime total comes back as 23,089,926.36 EGP, averaging 3,848.32 EGP per order.

ROUND matters for AVG

AVG keeps every decimal place MySQL computes (3848.321060) unless you wrap it in ROUND(..., 2) — almost always what you want for a currency figure.

10GROUP BY — aggregating per bucket

Aggregate functions (COUNT, SUM, AVG, MIN, MAX) collapse all matching rows into one number, unless you tell them to collapse separately per group:

Business question: which marketing channel drives the most web traffic overall?

day02_filtering_and_aggregation.sql
SELECT channel, COUNT(*) AS Cnt FROM web_events GROUP BY channel ORDER BY Cnt DESC;
The rule

Every column in SELECT that isn't wrapped in an aggregate function must appear in GROUP BY.

Multi-column groups

GROUP BY customer_id, channel gives one row per combination — this customer, that channel.

11HAVING — filtering grouped results

WHERE filters rows before grouping; HAVING filters groups after aggregation runs. That distinction matters because an aggregate like COUNT(*) or SUM(...) doesn't exist yet at the point WHERE is evaluated — only HAVING can filter on it.

Business question: which marketing channels actually moved the needle — more than 2,000 web events?

day02_filtering_and_aggregation.sql
SELECT channel, COUNT(*) AS Cnt FROM web_events GROUP BY channel HAVING COUNT(*) > 2000 ORDER BY Cnt DESC; -- WHERE COUNT(*) > 2000 here would be a syntax error — -- COUNT(*) doesn't exist yet at the point WHERE runs
Customers with more than 10 orders

GROUP BY customer_id HAVING COUNT(*) > 10 — same shape, a different single table.

Customers that spent under 2,000 EGP total

HAVING SUM(total_amount) < 2000 — HAVING works with any aggregate, not just COUNT.

Stacks with WHERE

Filter rows first with WHERE, then filter the resulting groups with HAVING — the two run at different stages, so a query can use both at once.

12DATE functions

MySQL pulls pieces out of a TIMESTAMP with dedicated functions: YEAR(), MONTH(), DAY(), HOUR(), DATE() (strips the time, keeps the date), MONTHNAME(), DAYNAME().

Business question: for a quarterly report, pull just the year out of every order's timestamp — three interchangeable ways to do it.

day02_filtering_and_aggregation.sql
-- three equivalent ways to get just the year SELECT YEAR(order_date) FROM orders; SELECT EXTRACT(YEAR FROM order_date) FROM orders; SELECT DATE_FORMAT(order_date, '%Y') FROM orders;
Pick one, be consistent

All three return the same value — YEAR() is usually the clearest to read back later.

Shifting and truncating dates

Business question: ops needs a delivery date, a "how stale is this order" figure, and monthly order counts — three common date-shifting needs.

day02_filtering_and_aggregation.sql
-- expected delivery = order date + 7 days SELECT order_date, DATE_ADD(order_date, INTERVAL 7 DAY) AS expected_delivery FROM orders; -- how many days ago did this order happen? SELECT order_date, DATEDIFF(CURDATE(), order_date) AS days_ago FROM orders; -- bucket every order into the month it happened, ignoring the day/time SELECT DATE_FORMAT(order_date, '%Y-%m') AS order_month, COUNT(*) FROM orders GROUP BY order_month;
DATE_ADD / DATE_SUB

DATE_ADD(date, INTERVAL n DAY) shifts a date forward; swap in DATE_SUB — or a negative interval — to shift backward. INTERVAL also accepts MONTH, YEAR, HOUR, and more.

DATEDIFF

Returns the number of days between two dates — handy for "how long ago," or for measuring the gap between an order date and a delivery date.

DATE_FORMAT + GROUP BY

This is how monthly/yearly reports get built: format every timestamp down to just 'YYYY-MM', then group on that string — every order in the same month collapses into one row. Watch for this pattern with Rawaj's own data: order volume genuinely spikes every year during Ramadan/Eid — a real seasonal signal, not noise.
