3WHERE — filtering rows

WHERE narrows which rows a query returns, evaluated before SELECT/ORDER BY/LIMIT get a chance to do anything — think of it as a gate that rows have to pass through first.

day02_filtering_and_aggregation.sql
SELECT * FROM orders WHERE total_amt_usd > 100000 ORDER BY total_amt_usd DESC;
Comparison operators

=, >, <, >=, <= all work exactly as you'd expect from arithmetic.

Not-equal, three ways

!=, <> (standard SQL), and WHERE NOT account_id = 1001 all mean the same thing — != is the one you'll see most in practice.

4AND / OR — combining conditions

AND — narrows

Both conditions must hold. channel = 'facebook' AND account_id = 1001 returns only Facebook events, and only for that one account — the smallest of the four possible result sets.

OR — widens

Either can hold. Swap in OR and you get every Facebook event from any account, plus every event (any channel) from account 1001 — often a much bigger, looser result than intended.

day02_filtering_and_aggregation.sql
-- AND: narrow — only Facebook events from account 1001 SELECT * FROM web_events WHERE channel = 'facebook' AND account_id = 1001; -- OR: wide — Facebook events from anyone, plus every event from account 1001 SELECT * FROM web_events WHERE channel = 'facebook' OR account_id = 1001;
Same shape, different meaning

Only the keyword changed — the row counts these two return can differ by an order of magnitude on a real dataset.

The most common real-world SQL bug

Mixing up AND/OR is grammatically valid in exactly the same spot but changes the result drastically — and MySQL will never warn you, because both versions are perfectly correct SQL. The only defense is reading each condition back and asking "does this describe what I actually mean?"

5BETWEEN — range filtering

WHERE total_amt_usd BETWEEN 500 AND 999 is shorthand for WHERE total_amt_usd >= 500 AND total_amt_usd <= 999 — both endpoints inclusive. It works on dates too: WHERE occurred_at BETWEEN '2014-12-30' AND '2015-01-01' — a pattern you'll use constantly once real reporting periods (last week, last quarter) enter the picture.

day02_filtering_and_aggregation.sql
-- numeric range SELECT id, total_amt_usd FROM orders WHERE total_amt_usd BETWEEN 500 AND 999; -- date range — same keyword, no numeric/date distinction to remember SELECT id, occurred_at FROM orders WHERE occurred_at BETWEEN '2014-12-30' AND '2015-01-01';
Written out with AND/OR, this gets long fast

WHERE total_amt_usd >= 500 AND total_amt_usd <= 999 says exactly the same thing — BETWEEN is purely a shorter way to write a two-sided AND.

6IN vs OR

day02_filtering_and_aggregation.sql
-- gets unwieldy fast WHERE channel = 'facebook' OR channel = 'twitter' OR channel = 'organic' -- identical result, one line WHERE channel IN ('facebook', 'twitter', 'organic')
NOT IN works too

Excludes every value in the list instead of matching it — handy for "everything except these three legacy channels."

7NULL checks

NULL means "no value was ever recorded here" — it is not 0, not an empty string '', and ordinary = silently fails to test for it (WHERE x = NULL matches nothing, with no error). Use IS NULL / IS NOT NULL instead.

Why this dataset won't show it

Parch & Posey happens to have no NULLs anywhere, so WHERE primary_poc IS NULL returns 0 rows here. The syntax is exactly what you'd reach for on a real, messier dataset — missing phone numbers, unfilled optional fields, a join that didn't find a match (you'll see that scenario properly on Day 03).

8LIKE — pattern matching

Two wildcards: % matches any number of characters (including zero), _ matches exactly one.

PatternMatches
'A%'starts with A
'%a%'contains a, anywhere
'_a%''a' is the 2nd character
'_a___'exactly 5 characters, 'a' 2nd
'%ct'ends with 'ct'

9GROUP BY — aggregating per bucket

Aggregate functions (COUNT, SUM, AVG, MIN, MAX) collapse all matching rows into one number, unless you tell them to collapse separately per group:

day02_filtering_and_aggregation.sql
SELECT channel, COUNT(*) AS Cnt FROM web_events GROUP BY channel ORDER BY Cnt DESC;
The rule

Every column in SELECT that isn't wrapped in an aggregate function must appear in GROUP BY.

Multi-column groups

GROUP BY account_id, channel gives one row per combination — this account, that channel.

10DATE functions

MySQL pulls pieces out of a TIMESTAMP with dedicated functions: YEAR(), MONTH(), DAY(), HOUR(), DATE() (strips the time, keeps the date), MONTHNAME(), DAYNAME().

day02_filtering_and_aggregation.sql
-- three equivalent ways to get just the year SELECT YEAR(occurred_at) FROM orders; SELECT EXTRACT(YEAR FROM occurred_at) FROM orders; SELECT DATE_FORMAT(occurred_at, '%Y') FROM orders;
Pick one, be consistent

All three return the same value — YEAR() is usually the clearest to read back later.

Shifting and truncating dates

day02_filtering_and_aggregation.sql
-- expected delivery = order date + 7 days SELECT occurred_at, DATE_ADD(occurred_at, INTERVAL 7 DAY) AS expected_delivery FROM orders; -- how many days ago did this order happen? SELECT occurred_at, DATEDIFF(CURDATE(), occurred_at) AS days_ago FROM orders; -- bucket every order into the month it happened, ignoring the day/time SELECT DATE_FORMAT(occurred_at, '%Y-%m') AS order_month, COUNT(*) FROM orders GROUP BY order_month;
DATE_ADD / DATE_SUB

DATE_ADD(date, INTERVAL n DAY) shifts a date forward; swap in DATE_SUB — or a negative interval — to shift backward. INTERVAL also accepts MONTH, YEAR, HOUR, and more.

DATEDIFF

Returns the number of days between two dates — handy for "how long ago," or for measuring the gap between an order date and a delivery date.

DATE_FORMAT + GROUP BY

This is how monthly/yearly reports get built: format every timestamp down to just 'YYYY-MM', then group on that string — every order in the same month collapses into one row.
