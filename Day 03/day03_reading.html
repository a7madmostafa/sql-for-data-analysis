JOINs, CASE & String Functions

Bringing every table together and labeling what you find, then cleaning and reshaping the text inside it — INNER · LEFT/RIGHT · anti-joins · UNION · HAVING · CASE · string functions.

What you'll be able to do after this lesson

  • Combine rows from multiple tables with JOIN, and know when a plain (INNER) JOIN silently drops rows you wanted.
  • Keep unmatched rows with LEFT/RIGHT JOIN, and use that same pattern to write an anti-join.
  • Emulate MySQL's missing FULL JOIN with UNION.
  • Aggregate and filter across joined tables with GROUP BY and HAVING.
  • Add conditional logic with CASE — labeling rows, and bucketing continuous values into tiers.
  • Trim, slice, and rebuild text with LTRIM/RTRIM/TRIM, LEFT/RIGHT/SUBSTRING/LOCATE, CONCAT, REPLACE, LOWER/UPPER/LENGTH.
  • Fill in gaps left by a CASE expression with COALESCE/IFNULL.
Before you start

This lesson reuses Day 02's parch_and_posey database — run Databases/Parch & Posey Database.sql first if you haven't already, then USE parch_and_posey;. No new setup script this time; today is about bringing all five tables together instead of querying one at a time.

1From relationships to JOINs

Day 01 introduced three relationship types. Today, they become real SQL.

Day 01 introduced 1:1, 1:N, and N:N using a primary key/foreign key pair. Here's the idea that connects that lesson to this one: JOIN is the SQL operation that follows a foreign key back to the row it points to. Every relationship type is just a different pattern of JOINs — and every table in parch_and_posey is chained together by exactly one of these two shapes.

1:N — one JOIN

region → sales_reps, sales_reps → accounts, accounts → orders/web_events. Every relationship in this dataset, and everything in today's lesson, is this shape.

N:N — two JOINs

Needs a junction table in the middle — Day 01's book↔author via book_author. Not present in this dataset, but recognize the shape when you see it elsewhere.

An N:N JOIN reaches the far side in two hops: book JOIN book_author ON ... JOIN author ON ... — one JOIN to get from book to the junction row, a second to get from the junction row to author. Today's lesson never needs this — parch_and_posey is 1:N end to end — but the technique is exactly this diagram, chained.

2Anatomy of a JOIN

skeleton
SELECT <columns> FROM <left_table> JOIN <right_table> ON <left_table>.<fk_column> = <right_table>.<pk_column>;

ON is the join condition — it tells MySQL which rows from each table belong together, by matching a foreign key on one side to the primary key it points to on the other. Table aliases (FROM orders o JOIN accounts a) exist because real queries reference the same table names repeatedly — o.account_id = a.id is a lot less noisy than spelling out orders.account_id = accounts.id every time, especially once you're joining three or four tables.

Get ON wrong and you get a cross join

Omit ON, or write a condition that doesn't actually relate the two tables, and MySQL pairs every row of the left table with every row of the right table. For orders × accounts in this dataset, that's tens of thousands of nonsense rows — not an error, just silently wrong data.

3INNER JOIN basics

Plain JOIN is shorthand for INNER JOIN — it returns only the rows that find a match on both sides.

Business question: Finance wants order and account details together in one view — combine every order with the account that placed it.

day03_joins_case_and_strings.sql
SELECT orders.id, accounts.name, orders.occurred_at FROM orders JOIN accounts ON orders.account_id = accounts.id; -- same thing, with aliases SELECT o.id, a.name, o.occurred_at FROM orders AS o JOIN accounts AS a ON o.account_id = a.id;
AS is optional

FROM orders o works identically to FROM orders AS o — most people drop the AS for table aliases even while keeping it for column aliases.

Columns from both sides

Once tables are joined, you pick columns from either one in the same SELECT list — o.occurred_at and a.name live in different tables but read like one combined row.

4Multi-table JOINs

Each additional JOIN follows one more foreign key — chaining three or four tables together is just repeating the pattern from Section 2.

Business question: leadership wants to trace every order back to the sales rep who owns that account, and regional management wants a per-order unit price broken out by region.

day03_joins_case_and_strings.sql
-- 3 tables: orders -> accounts -> sales_reps SELECT * FROM orders o JOIN accounts a ON o.account_id = a.id JOIN sales_reps s ON a.sales_rep_id = s.id; -- 4 tables, computing a unit price per order SELECT r.name AS region, a.name AS account, o.total_amt_usd / (o.total + 0.01) AS unit_price FROM orders o JOIN accounts a ON o.account_id = a.id JOIN sales_reps s ON a.sales_rep_id = s.id JOIN region r ON s.region_id = r.id;
Order rarely matters

MySQL works out the join order internally — write the JOINs in whatever sequence reads clearest, usually following the FK chain from the table you care about most.

+ 0.01 trick

A cheap guard against dividing by zero on the handful of orders where total happens to be 0 — shifts the denominator just enough to avoid an error without meaningfully changing the result.

Each JOIN = one more hop

region → sales_reps → accounts → orders — four tables, three JOINs, following the same chain diagrammed back in Day 02.

5JOIN + GROUP BY

Nothing new syntactically — the JOIN happens first, combining rows from multiple tables, and GROUP BY then works on the result exactly as it did in Day 02.

Business question: which accounts generate the most total revenue, and how often does each sales rep's accounts use each marketing channel?

day03_joins_case_and_strings.sql
SELECT a.name AS account_name, SUM(o.total_amt_usd) AS total_sales FROM orders o JOIN accounts a ON o.account_id = a.id GROUP BY a.name ORDER BY total_sales DESC; SELECT s.name, w.channel, COUNT(*) AS occurrences FROM web_events w JOIN accounts a ON w.account_id = a.id JOIN sales_reps s ON s.id = a.sales_rep_id GROUP BY s.name, w.channel ORDER BY occurrences DESC;
Same GROUP BY rule as Day 02

Every non-aggregated column in SELECT — s.name, w.channel — still has to appear in GROUP BY, whether it came from a JOIN or not.

6JOIN + HAVING

HAVING was introduced back in Day 02 for filtering aggregates on a single table. Nothing about it changes here — the JOIN just means the group being filtered can now span multiple tables.

Business question: which sales reps manage more than 5 accounts — are any of them overloaded?

day03_joins_case_and_strings.sql
-- sales reps who manage more than 5 accounts SELECT s.id, s.name, COUNT(*) AS num_accounts FROM accounts a JOIN sales_reps s ON s.id = a.sales_rep_id GROUP BY s.id, s.name HAVING COUNT(*) > 5; -- WHERE COUNT(*) > 5 here would be a syntax error — -- COUNT(*) doesn't exist yet at the point WHERE runs
Accounts with more than 20 orders

GROUP BY a.id, a.name HAVING COUNT(*) > 20 — same shape, different table pair.

Accounts that spent under $1,000 total

HAVING SUM(o.total_amt_usd) < 1000 — HAVING works with any aggregate, not just COUNT.

7LEFT / RIGHT JOIN

LEFT JOIN keeps every row from the left table regardless of whether a match exists on the right — unmatched columns from the right table come back NULL instead of dropping the row. RIGHT JOIN is the mirror image: keep everything on the right, matched or not.

Business question: which accounts exist, whether or not they've ever placed an order — and, mirrored, which orders exist even if their account record can no longer be resolved?

day03_joins_case_and_strings.sql
-- every account, whether or not it has orders SELECT * FROM accounts LEFT JOIN orders ON orders.account_id = accounts.id; -- every order, even if its account can't be resolved SELECT * FROM orders RIGHT JOIN accounts ON orders.account_id = accounts.id; -- OUTER is optional noise: LEFT OUTER JOIN == LEFT JOIN
Unmatched side = NULL

Every column from the table that didn't find a match comes back NULL for that row — the row itself still shows up.

8Anti-joins — finding non-matches

A LEFT JOIN plus WHERE ... IS NULL isolates exactly the rows that found no match — this pattern is called an anti-join.

Business question: which accounts have NEVER placed a single order — a churn/onboarding red-flag list for the sales team?

day03_joins_case_and_strings.sql
-- accounts with NO orders at all SELECT * FROM accounts a LEFT JOIN orders o ON a.id = o.account_id WHERE o.id IS NULL;
Why this works

Every unmatched row has o.id — and every other orders column — as NULL. Filtering on that isolates exactly the accounts the LEFT JOIN couldn't match, same Delta LLC row from the diagram above.

A very common real question

"Which customers/leads never converted" or "which accounts have never ordered" is almost always this exact pattern — LEFT JOIN toward the table you expect a match in, then filter for where it didn't happen.

9FULL JOIN — MySQL has no such keyword

Some databases support FULL JOIN directly (everything from both sides, matched or not). MySQL doesn't — you get the same result by taking the UNION of a LEFT JOIN and a RIGHT JOIN.

Business question: compliance wants a single report covering every order-account relationship — matched, order-only, and account-only rows, all at once.

day03_joins_case_and_strings.sql
SELECT * FROM orders LEFT JOIN accounts ON orders.account_id = accounts.id UNION SELECT * FROM orders RIGHT JOIN accounts ON orders.account_id = accounts.id;
UNION drops duplicates

Rows that matched appear in both halves (the LEFT JOIN result and the RIGHT JOIN result) but UNION only keeps one copy — UNION ALL would keep both if you ever wanted the duplicates.

Same column count required

Both SELECTs must return the same number of columns, in compatible types — MySQL matches them up positionally, not by name.

10CASE — conditional logic inside a query

skeleton
CASE WHEN <condition_1> THEN <result_1> WHEN <condition_2> THEN <result_2> ELSE <fallback> END AS <column_alias>

Conditions are checked top to bottom — the first one that's true wins, and the rest are skipped, so order matters whenever ranges could overlap. ELSE is optional; without it, rows that hit no WHEN come back NULL instead of a fallback value.

Business question: flag every order "Large" or "Small" for a dashboard, and compute a safe per-unit price that won't crash on zero-quantity orders.

day03_joins_case_and_strings.sql
SELECT id, account_id, total_amt_usd, CASE WHEN total_amt_usd > 2000 THEN 'Large' ELSE 'Small' END AS order_level FROM orders; -- CASE can guard against bad math, too SELECT account_id, CASE WHEN standard_qty = 0 OR standard_qty IS NULL THEN 0 ELSE standard_amt_usd / standard_qty END AS unit_price FROM orders;
Works anywhere an expression can go

SELECT to label rows, wrapped in an aggregate (SUM(CASE WHEN ... THEN 1 ELSE 0 END) is a conditional count), or referenced in GROUP BY/HAVING/ORDER BY by its alias.

11CASE + GROUP BY — bucketing into tiers

A CASE inside — or alongside — an aggregate is how you bucket continuous values (order totals, account lifetime spend) into discrete tiers for reporting, with no separate lookup table required.

Business question: bucket every order into a size category for reporting, and rank every account into top/middle/low lifetime-value tiers based on total spend.

day03_joins_case_and_strings.sql
-- bucket every order into a size category, then count each bucket SELECT CASE WHEN total >= 2000 THEN 'At Least 2000' WHEN total BETWEEN 1000 AND 2000 THEN 'Between 1000 and 2000' ELSE 'Less than 1000' END AS order_category, COUNT(*) AS order_count FROM orders GROUP BY 1; -- customer lifetime value tiers, based on total spend per account SELECT a.name, SUM(o.total_amt_usd) AS total_spent, CASE WHEN SUM(o.total_amt_usd) > 200000 THEN 'top' WHEN SUM(o.total_amt_usd) > 100000 THEN 'middle' ELSE 'low' END AS customer_level FROM orders o JOIN accounts a ON o.account_id = a.id GROUP BY a.name ORDER BY total_spent DESC;
GROUP BY 1

Groups by the first column in SELECT — here, the CASE expression itself — instead of repeating the whole CASE block a second time in GROUP BY.

CASE around an aggregate

The condition checks SUM(...), not a raw column — it's evaluated once per group, after the aggregation, not per row.

Order of WHENs matters

First match wins — the widest, catch-all range ('low' here) has to come last, or it would swallow everything above it too.

12CASE + HAVING

HAVING treats a CASE-derived value like any other aggregate result — you can filter on the same expression a CASE uses to decide its label.

Business question: which sales reps fall specifically in the "under $5k total sales" category — reps who might need extra support?

day03_joins_case_and_strings.sql
SELECT s.name, SUM(o.total_amt_usd) AS total_sales, CASE WHEN SUM(o.total_amt_usd) BETWEEN 1 AND 5000 THEN 'Under 5k' WHEN SUM(o.total_amt_usd) BETWEEN 5001 AND 10000 THEN '5-10k' ELSE '+10k' END AS sales_category FROM accounts a JOIN orders o ON a.id = o.account_id JOIN sales_reps s ON s.id = a.sales_rep_id GROUP BY a.id, a.sales_rep_id, s.name HAVING SUM(o.total_amt_usd) BETWEEN 1 AND 5000;
HAVING re-checks the condition directly

It re-evaluates SUM(o.total_amt_usd) itself here — MySQL doesn't let HAVING reuse the CASE expression's own alias for filtering, only for display.

Halfway point

Sections 1–10 covered combining and labeling rows across tables. The rest of this lesson is about cleaning and reshaping the text inside those rows.

11Trimming whitespace

Real data is rarely clean — exports and manual entry leave stray spaces around text.

FunctionRemoves
LTRIM(str)Leading (left-side) spaces only.
RTRIM(str)Trailing (right-side) spaces only.
TRIM(str)Both sides at once.

Business question: a CSV export from a legacy CRM padded every point-of-contact name with stray spaces — clean it up before the data gets loaded anywhere else.

day03_joins_case_and_strings.sql
SELECT LTRIM(' Alexander Freberg') AS left_trim; SELECT RTRIM('Alexander Freberg ') AS right_trim; SELECT TRIM(' Alexander Freberg ') AS trim_both;
Only whitespace, by default

Plain TRIM(str) strips spaces. MySQL's fuller form, TRIM(BOTH '.' FROM str), trims a specific character instead — rarely needed, but good to know it exists.

12Extracting parts of a string

LEFT/RIGHT grab a fixed number of characters from either end; SUBSTRING grabs a slice from any starting position; LOCATE finds where a character sits so the other three don't have to hardcode a position.

Business question: marketing wants a 4-letter account-code abbreviation for a print report, and a data-quality check that every account's website follows the expected www.company.com pattern.

day03_joins_case_and_strings.sql
SELECT name, LEFT(name, 4) AS account_code FROM accounts; -- SUBSTRING(str, start, length) — 1-indexed, same indexing LOCATE returns -- every website looks like 'www.walmart.com' — this pulls out everything before the FIRST dot SELECT website, SUBSTRING(website, 1, LOCATE('.', website) - 1) AS website_prefix FROM accounts; SELECT primary_poc, LOCATE(' ', primary_poc) AS space_position FROM accounts;
LOCATE is 1-indexed, and 0 means "not found"

Unlike most programming languages, position 1 is the first character — and if the search string never appears, LOCATE returns 0, not -1 or NULL.

Finds the FIRST match only

website has two dots (www.walmart.com) — LOCATE('.', website) stops at the first one, so this extracts 'www', not the company name. Getting the middle segment would need a second LOCATE starting after the first match — not needed for today's lesson, but worth knowing the limit.

The -1 in this example

LOCATE('.', website) - 1 is the length of everything before the dot — feeding that as the length argument to SUBSTRING is how Section 13's email-builder finds a name split too.

13Building and cleaning strings

CONCAT glues pieces together; REPLACE swaps every occurrence of one substring for another; LOWER/ UPPER normalize case; LENGTH counts characters.

Business question: sales wants a company email address auto-generated for every point of contact — firstname.lastname@accountname.com, all lowercase, no spaces.

day03_joins_case_and_strings.sql
WITH name_split AS ( SELECT REPLACE(name, ' ', '') AS clean_account_name, LEFT(primary_poc, LOCATE(' ', primary_poc) - 1) AS first_name, RIGHT(primary_poc, LENGTH(primary_poc) - LOCATE(' ', primary_poc)) AS last_name FROM accounts ) SELECT first_name, last_name, CONCAT(LOWER(first_name), '.', LOWER(last_name), '@', LOWER(clean_account_name), '.com') AS email FROM name_split;
Don't worry about WITH yet

This is a CTE (Day 04 covers the syntax properly) — it's used here only so the first/last-name split doesn't have to be repeated three times inside one long SELECT.

Each piece is one function, chained

LEFT + LOCATE gets the first name, RIGHT + LENGTH + LOCATE gets the last name, REPLACE strips spaces from the account name — then CONCAT stitches all of it together.

14COALESCE / IFNULL — filling in the gaps

A CASE that doesn't cover every possibility leaves some rows NULL (Section 8 covered this with ELSE). IFNULL(expr, fallback) swaps in a fallback value wherever expr is NULL — a lighter-weight fix than adding another WHEN. COALESCE does the same thing but accepts any number of arguments, returning the first one that isn't NULL — IFNULL is really just MySQL's two-argument shortcut for it.

Business question: bucket every order by item count, but the defined buckets only cover 0–100 and 101–200 — anything bigger needs to read "200+" instead of a blank cell on the dashboard.

day03_joins_case_and_strings.sql
WITH total_range AS ( SELECT CASE WHEN total BETWEEN 0 AND 100 THEN '0-100' WHEN total BETWEEN 101 AND 200 THEN '101-200' END AS total_range FROM orders ) SELECT IFNULL(total_range, '200+') AS total_range FROM total_range;
No ELSE means NULL, on purpose

Leaving the CASE without an ELSE is what creates the gap IFNULL then fills — the two techniques are meant to pair together, not compete.
