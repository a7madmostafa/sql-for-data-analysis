Window Functions & Stored Procedures

Ranking and running totals without collapsing rows, then reusable logic saved inside the database itself.

What you'll be able to do after this lesson

  • Compute a running total, rank, or row-to-row comparison with a window function, without collapsing rows the way GROUP BY does.
  • Reset a window per group with PARTITION BY, and tell RANK/DENSE_RANK/ROW_NUMBER apart by how each handles ties.
  • Look at a neighboring row with LAG/LEAD, for month-over-month style comparisons.
  • Write, and CALL, a stored procedure with IN and OUT parameters, using DELIMITER correctly.

Window functions need MySQL 8.0 or newer

Everything in Sections 1–5 was added to MySQL in version 8.0. On an older server (5.7 and below) every one of these queries fails with a syntax error pointing at OVER. Check before you start:

SELECT VERSION(); — if the number starts with 8. or higher you're fine. If it starts with 5., upgrade before working through this day; there is no workaround short of rewriting each query as a correlated subquery.

1Window functions — OVER, without collapsing rows

Every aggregate so far (SUM, COUNT, AVG...) needed GROUP BY, and GROUP BY always collapses many rows into one per group. A window function computes that same kind of aggregate, but keeps every row — each one just gains an extra column computed by looking through a "window" of other rows, defined by OVER (...).

Business question: finance wants to see revenue build up over time — a running total, not a single company-wide sum.

day05_window_functions_and_stored_procedures.sql
SELECT order_date, total_amount, SUM(total_amount) OVER (ORDER BY order_date) AS running_total FROM orders ORDER BY order_date LIMIT 10;
OVER is what makes it a window function

Drop the OVER (...) and this is a plain aggregate needing GROUP BY. Add it, and SUM instead computes a value per row, looking at the set of rows ORDER BY defines as "so far."

The window's ORDER BY is independent

ORDER BY order_date inside OVER(...) controls calculation order (which rows count as "before" this one) — a separate, outer ORDER BY would control display order, and both are usually the same column here.

A gotcha worth knowing early

SUM(...) OVER (ORDER BY col) with no explicit frame clause defaults to RANGE UNBOUNDED PRECEDING, which means "every row whose ordering value is less than or equal to this one." So if two rows tie on the ordering column, they both get the same cumulative total — the one that includes both of them — rather than one stepping past the other. Ordering on something unique (a timestamp, an id) sidesteps it; ROWS UNBOUNDED PRECEDING forces strict row-by-row accumulation if you need it.

2PARTITION BY — resetting the window per group

PARTITION BY inside OVER(...) is to a window function what GROUP BY is to a plain aggregate — it restarts the calculation every time the partition column's value changes, without collapsing any rows.

Business question: the same running total, but per customer — not one company-wide number mixing every customer together.

day05_window_functions_and_stored_procedures.sql
SELECT customer_id, order_date, total_amount, SUM(total_amount) OVER (PARTITION BY customer_id ORDER BY order_date) AS customer_running_total FROM orders ORDER BY customer_id, order_date;
Order inside OVER matters

PARTITION BY always comes before ORDER BY inside the same OVER(...) — think "which group, then in what order within it."

3RANK, DENSE_RANK, ROW_NUMBER

All three number rows 1, 2, 3... in the order OVER (ORDER BY ...) defines — they only disagree once two rows tie on that ordering column.

FunctionOn a tie (e.g. two rows both rank 2nd)
ROW_NUMBER()Always unique — arbitrarily breaks the tie, never repeats a number: 1, 2, 3, 4.
RANK()Tied rows share a number, then skips ahead by how many tied: 1, 2, 2, 4.
DENSE_RANK()Tied rows share a number, but never skips: 1, 2, 2, 3.

Seeing the difference on three rows

The table above is easier to trust once you watch it happen. This query invents three rows with a deliberate tie — A and B both on 100 — and runs all three functions over them. No table needed, so you can paste it into any MySQL 8 client:

tie demo — paste anywhere
SELECT name, v, RANK() OVER (ORDER BY v DESC) AS rnk, DENSE_RANK() OVER (ORDER BY v DESC) AS dense_rnk, ROW_NUMBER() OVER (ORDER BY v DESC) AS row_num FROM ( SELECT 'A' AS name, 100 AS v UNION ALL SELECT 'B', 100 UNION ALL SELECT 'C', 90 ) t ORDER BY v DESC;

A100111

C90323

Read the bottom row across: RANK jumped to 3 (it burned number 2 on the tie), DENSE_RANK stayed at 2 (no gap), and ROW_NUMBER never repeated a number at all — it broke the A/B tie arbitrarily. That's the whole distinction, on three rows.

Why the invented data

The Rawaj query below has no ties — all five managers land on different totals, so all three columns read 1, 2, 3, 4, 5 and the functions look identical. That's typical of real data with money in it, which is exactly why the difference is worth learning from a rigged three-row example first.

Business question: leadership wants account managers ranked by total sales — and wants to know exactly how ties get handled, since two managers landing on the same revenue isn't rare.

day05_window_functions_and_stored_procedures.sql
WITH manager_totals AS ( SELECT am.manager_id, am.manager_name, SUM(o.total_amount) AS total_sales FROM orders o JOIN customers c ON o.customer_id = c.customer_id JOIN governorates g ON c.governorate_id = g.governorate_id JOIN account_managers am ON g.manager_id = am.manager_id GROUP BY am.manager_id, am.manager_name ) SELECT manager_name, total_sales, RANK() OVER (ORDER BY total_sales DESC) AS rank_with_gaps, DENSE_RANK() OVER (ORDER BY total_sales DESC) AS dense_rank_no_gaps, ROW_NUMBER() OVER (ORDER BY total_sales DESC) AS row_num FROM manager_totals ORDER BY total_sales DESC;
CTE first, ranking second

All three ranking functions need manager_totals already computed — the same CTE pattern from Day 04's Section 4, now feeding a window function instead of a plain SELECT.

Which one to reach for

DENSE_RANK for gapless tiers ("top 3 revenue tiers"), RANK when a skipped number should reflect competition (like a race), ROW_NUMBER whenever you need exactly one row per rank no matter what — the next section depends on that guarantee.

4Ranking within a partition, then filtering to one per group

A window function can't be filtered directly in WHERE — the same rule that blocks WHERE COUNT(*) > 5 (Day 02). The analogy stops one step short, though: unlike aggregates, HAVING doesn't help either, because window functions are evaluated after HAVING — a window function can only be filtered from an outer query, CTE, or subquery. Compute the rank in a CTE first, then filter the CTE's output.

Business question: for every customer, what was their single largest order? (Same shape as Day 04's Section 1 subquery question — a window function reaches the same answer more directly.)

day05_window_functions_and_stored_procedures.sql
WITH ranked_orders AS ( SELECT customer_id, order_id, total_amount, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY total_amount DESC) AS order_rank FROM orders ) SELECT customer_id, order_id, total_amount FROM ranked_orders WHERE order_rank = 1 ORDER BY customer_id;
PARTITION BY here means "per customer"

Without it, this would rank every order in the whole table against each other — PARTITION BY customer_id is what makes rank 1 mean "this customer's biggest order," restarting for each customer.

ROW_NUMBER, not RANK, for a "one per group" filter

This is the guarantee Section 3 pointed at. If a customer's two biggest orders happened to be for the identical amount, RANK would give both rank 1 and the query would return two rows for that customer — quietly breaking "one row per customer." ROW_NUMBER can't do that, so exactly one row comes back per customer no matter what the data does.

5LAG / LEAD — comparing a row to a neighbor

LAG(col) looks one row back (in whatever order OVER (ORDER BY ...) defines); LEAD(col) looks one row forward. Both default to an offset of 1 — LAG(col, 2) would look back two rows instead.

Business question: is month-over-month revenue growing or shrinking?

day05_window_functions_and_stored_procedures.sql
WITH monthly_sales AS ( SELECT DATE_FORMAT(order_date, '%Y-%m') AS month, SUM(total_amount) AS total_sales FROM orders GROUP BY month ) SELECT month, total_sales, LAG(total_sales) OVER (ORDER BY month) AS prev_month_sales, LEAD(total_sales) OVER (ORDER BY month) AS next_month_sales, total_sales - LAG(total_sales) OVER (ORDER BY month) AS change_from_prev_month FROM monthly_sales ORDER BY month;
The first row has nothing to look back to

LAG returns NULL for the very first month — expected behavior, not a bug, same as any window function at the edge of its data. LEAD has the mirror-image problem: the last month has nothing ahead of it, so its next_month_sales is NULL too.

LAG and LEAD are the same function pointing opposite ways

Both take an offset that defaults to 1. LEAD(total_sales) here is just "the value one row further down, in month order" — handy when you want each row to carry both its history and what came next, without self-joining the table to itself.

What the output actually shows

Run this and one pair of months leaps out. February 2024 totals 666,832.47 EGP; March 2024 totals 2,937,664.69 EGP — roughly 4.4× the month before, a jump of over 2.27 million EGP. April stays elevated at 1,936,906.62 EGP, then May drops back to 652,697.27 EGP, right onto the ordinary baseline of roughly 600–800k that every other month sits at.

Ramadan fell in March 2024, with Eid al-Fitr at its end and Eid shopping running into April. That two-month bulge and its snap back to baseline is the single largest signal in Rawaj's order history — and it is exactly the kind of thing a month-over-month LAG column exists to surface. A plain SUM ... GROUP BY month would list the same numbers; the change_from_prev_month column is what makes the spike impossible to scroll past.

6Stored procedures (IN parameters)

skeleton
DELIMITER $$ CREATE PROCEDURE <procedure_name>(IN <param_name> <type>) BEGIN <one or more SQL statements>; END$$ DELIMITER ; CALL <procedure_name>(<value>);

A stored procedure is a named, reusable block of SQL logic saved inside the database itself — call it by name instead of re-pasting the same query every time someone needs it. An IN parameter passes a value into the procedure, the way a function argument would in any programming language.

Why DELIMITER is required here

Running this file as a script (the mysql CLI, source, or Workbench's "execute script") splits statements on every plain semicolon. Without switching the delimiter first, it would try to run BEGIN ... SELECT ...; as a complete statement and choke on the very first semicolon inside the procedure body. DELIMITER $$ temporarily changes the statement terminator to $$, so the whole CREATE PROCEDURE ... END block is read as one statement; DELIMITER ; switches it back afterward. This becomes unnecessary in Day 06, once SQL is sent through a Python driver instead — a Python driver sends the whole block as one request, with no client-side statement-splitting involved at all.

Business question: account managers constantly ask for the same report — order count and total revenue for one customer. Save it once as a procedure everyone can call.

day05_window_functions_and_stored_procedures.sql
-- re-running CREATE PROCEDURE without dropping first fails with -- ERROR 1304: PROCEDURE customer_sales_report already exists DROP PROCEDURE IF EXISTS customer_sales_report; DELIMITER $$ CREATE PROCEDURE customer_sales_report(IN cust_id INT) BEGIN SELECT c.first_name, c.last_name, COUNT(o.order_id) AS num_orders, SUM(o.total_amount) AS total_sales FROM customers c JOIN orders o ON o.customer_id = c.customer_id WHERE c.customer_id = cust_id GROUP BY c.first_name, c.last_name; END$$ DELIMITER ; CALL customer_sales_report(1);
The parameter, used inside the body

cust_id works exactly like a variable inside BEGIN...END — whatever value CALL passes in gets substituted wherever cust_id appears.

7Stored procedures (OUT parameters)

An OUT parameter hands a value back through a user session variable (conventionally written @name) instead of a result set — useful when the caller is another program that needs one number to act on, not a table to read. SELECT ... INTO <out_param> is how the procedure body assigns it.

Business question: a nightly batch job needs just the single number — total company-wide revenue — captured into a variable it can act on.

day05_window_functions_and_stored_procedures.sql
DROP PROCEDURE IF EXISTS get_total_revenue; DELIMITER $$ CREATE PROCEDURE get_total_revenue(OUT total_revenue DECIMAL(14,2)) BEGIN SELECT SUM(total_amount) INTO total_revenue FROM orders; END$$ DELIMITER ; CALL get_total_revenue(@rev); SELECT @rev AS total_revenue;
Enough to read one, not to design one

This is enough to recognize a stored procedure when you meet one in a real codebase, and to know what IN/OUT parameters do — the SQL inside is everything you already know from Days 01–04.
