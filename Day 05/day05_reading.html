Window Functions & Stored Procedures

Ranking and running totals without collapsing rows, then reusable logic saved inside the database itself.

What you'll be able to do after this lesson

  • Compute a running total, rank, or row-to-row comparison with a window function, without collapsing rows the way GROUP BY does.
  • Reset a window per group with PARTITION BY, and tell RANK/DENSE_RANK/ROW_NUMBER apart by how each handles ties.
  • Look at a neighboring row with LAG/LEAD, for month-over-month style comparisons.
  • Write, and CALL, a stored procedure with IN and OUT parameters, using DELIMITER correctly.
Before you start

Continuing straight on from Day 04, still the same rawaj database — run Databases/rawaj_db.sql first if you haven't already, then USE rawaj;. No new setup script today.

1Window functions — OVER, without collapsing rows

Every aggregate so far (SUM, COUNT, AVG...) needed GROUP BY, and GROUP BY always collapses many rows into one per group. A window function computes that same kind of aggregate, but keeps every row — each one just gains an extra column computed by looking through a "window" of other rows, defined by OVER (...).

Business question: finance wants to see revenue build up over time — a running total, not a single company-wide sum.

day05_window_functions_and_stored_procedures.sql
SELECT order_date, total_amount, SUM(total_amount) OVER (ORDER BY order_date) AS running_total FROM orders ORDER BY order_date LIMIT 10;
OVER is what makes it a window function

Drop the OVER (...) and this is a plain aggregate needing GROUP BY. Add it, and SUM instead computes a value per row, looking at the set of rows ORDER BY defines as "so far."

The window's ORDER BY is independent

ORDER BY occurred_at inside OVER(...) controls calculation order (which rows count as "before" this one) — a separate, outer ORDER BY would control display order, and both are usually the same column here.

2PARTITION BY — resetting the window per group

PARTITION BY inside OVER(...) is to a window function what GROUP BY is to a plain aggregate — it restarts the calculation every time the partition column's value changes, without collapsing any rows.

Business question: the same running total, but per account — not one company-wide number mixing every customer together.

day05_window_functions_and_stored_procedures.sql
SELECT customer_id, order_date, total_amount, SUM(total_amount) OVER (PARTITION BY customer_id ORDER BY order_date) AS customer_running_total FROM orders ORDER BY customer_id, order_date;
Order inside OVER matters

PARTITION BY always comes before ORDER BY inside the same OVER(...) — think "which group, then in what order within it."

3RANK, DENSE_RANK, ROW_NUMBER

All three number rows 1, 2, 3... in the order OVER (ORDER BY ...) defines — they only disagree once two rows tie on that ordering column.

FunctionOn a tie (e.g. two rows both rank 2nd)
ROW_NUMBER()Always unique — arbitrarily breaks the tie, never repeats a number: 1, 2, 3, 4.
RANK()Tied rows share a number, then skips ahead by how many tied: 1, 2, 2, 4.
DENSE_RANK()Tied rows share a number, but never skips: 1, 2, 2, 3.

Business question: leadership wants account managers ranked by total sales — and wants to know exactly how ties get handled, since two managers landing on the same revenue isn't rare.

day05_window_functions_and_stored_procedures.sql
WITH manager_totals AS ( SELECT am.manager_id, am.manager_name, SUM(o.total_amount) AS total_sales FROM orders o JOIN customers c ON o.customer_id = c.customer_id JOIN governorates g ON c.governorate_id = g.governorate_id JOIN account_managers am ON g.manager_id = am.manager_id GROUP BY am.manager_id, am.manager_name ) SELECT manager_name, total_sales, RANK() OVER (ORDER BY total_sales DESC) AS rank_with_gaps, DENSE_RANK() OVER (ORDER BY total_sales DESC) AS dense_rank_no_gaps, ROW_NUMBER() OVER (ORDER BY total_sales DESC) AS row_num FROM manager_totals ORDER BY total_sales DESC;
CTE first, ranking second

All three ranking functions need rep_totals already computed — the same CTE pattern from Day 04's Section 4, now feeding a window function instead of a plain SELECT.

Which one to reach for

DENSE_RANK for gapless tiers ("top 3 revenue tiers"), RANK when a skipped number should reflect competition (like a race), ROW_NUMBER whenever you need exactly one row per rank no matter what — the next section depends on that guarantee.

4Ranking within a partition, then filtering to one per group

A window function can't be filtered directly in WHERE — the same rule that blocks WHERE COUNT(*) > 5 (Day 03). Compute the rank in a CTE first, then filter the CTE's output.

Business question: for every customer, what was their single largest order? (Same shape as Day 04's Section 1 subquery question — a window function reaches the same answer more directly.)

day05_window_functions_and_stored_procedures.sql
WITH ranked_orders AS ( SELECT customer_id, order_id, total_amount, RANK() OVER (PARTITION BY customer_id ORDER BY total_amount DESC) AS order_rank FROM orders ) SELECT customer_id, order_id, total_amount FROM ranked_orders WHERE order_rank = 1 ORDER BY customer_id;
PARTITION BY here means "per customer"

Without it, this would rank every order in the whole table against each other — PARTITION BY customer_id is what makes rank 1 mean "this customer's biggest order," restarting for each customer.

5LAG / LEAD — comparing a row to a neighbor

LAG(col) looks one row back (in whatever order OVER (ORDER BY ...) defines); LEAD(col) looks one row forward. Both default to an offset of 1 — LAG(col, 2) would look back two rows instead.

Business question: is month-over-month revenue growing or shrinking?

day05_window_functions_and_stored_procedures.sql
WITH monthly_sales AS ( SELECT DATE_FORMAT(order_date, '%Y-%m') AS month, SUM(total_amount) AS total_sales FROM orders GROUP BY month ) SELECT month, total_sales, LAG(total_sales) OVER (ORDER BY month) AS prev_month_sales, total_sales - LAG(total_sales) OVER (ORDER BY month) AS change_from_prev_month FROM monthly_sales ORDER BY month;
The first row has nothing to look back to

LAG returns NULL for the very first month — expected behavior, not a bug, same as any window function at the edge of its data.

6Stored procedures (IN parameters)

skeleton
DELIMITER $$ CREATE PROCEDURE <procedure_name>(IN <param_name> <type>) BEGIN <one or more SQL statements>; END$$ DELIMITER ; CALL <procedure_name>(<value>);

A stored procedure is a named, reusable block of SQL logic saved inside the database itself — call it by name instead of re-pasting the same query every time someone needs it. An IN parameter passes a value into the procedure, the way a function argument would in any programming language.

Why DELIMITER is required here

Running this file as a script (the mysql CLI, source, or Workbench's "execute script") splits statements on every plain semicolon. Without switching the delimiter first, it would try to run BEGIN ... SELECT ...; as a complete statement and choke on the very first semicolon inside the procedure body. DELIMITER $$ temporarily changes the statement terminator to $$, so the whole CREATE PROCEDURE ... END block is read as one statement; DELIMITER ; switches it back afterward. This becomes unnecessary in Day 06, once SQL is sent through a Python driver instead — a Python driver sends the whole block as one request, with no client-side statement-splitting involved at all.

Business question: account managers constantly ask for the same report — order count and total revenue for one customer. Save it once as a procedure everyone can call.

day05_window_functions_and_stored_procedures.sql
DELIMITER $$ CREATE PROCEDURE customer_sales_report(IN cust_id INT) BEGIN SELECT c.first_name, c.last_name, COUNT(o.order_id) AS num_orders, SUM(o.total_amount) AS total_sales FROM customers c JOIN orders o ON o.customer_id = c.customer_id WHERE c.customer_id = cust_id GROUP BY c.first_name, c.last_name; END$$ DELIMITER ; CALL customer_sales_report(1);
The parameter, used inside the body

cust_id works exactly like a variable inside BEGIN...END — whatever value CALL passes in gets substituted wherever cust_id appears.

7Stored procedures (OUT parameters)

An OUT parameter hands a value back through a user session variable (conventionally written @name) instead of a result set — useful when the caller is another program that needs one number to act on, not a table to read. SELECT ... INTO <out_param> is how the procedure body assigns it.

Business question: a nightly batch job needs just the single number — total company-wide revenue — captured into a variable it can act on.

day05_window_functions_and_stored_procedures.sql
DELIMITER $$ CREATE PROCEDURE get_total_revenue(OUT total_revenue DECIMAL(14,2)) BEGIN SELECT SUM(total_amount) INTO total_revenue FROM orders; END$$ DELIMITER ; CALL get_total_revenue(@rev); SELECT @rev AS total_revenue;
Kept intentionally shallow

This is enough to read a stored procedure when you meet one in a real codebase — this is a data-analysis course, not a backend/app-dev one, so writing elaborate procedures isn't the goal here.
