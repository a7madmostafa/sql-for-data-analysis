1What is SQL?

Structured Query Language — the language you use to talk to a database.

Think about how you get information out of a spreadsheet: you scroll, you sort a column, maybe you write a filter formula. A database holds the same kind of tabular data, but usually far more of it — millions or billions of rows, spread across dozens of related tables. Scrolling isn't an option. Instead, you write a precise, structured sentence describing exactly what you want, and the database engine goes and gets it. That sentence is SQL.

SQL was created at IBM in the early 1970s (originally called SEQUEL) to work with a new idea at the time — the relational model, where data lives in tables connected by shared keys instead of rigid hierarchical file structures. It was standardized by ANSI in 1986 and by ISO shortly after, which is why the core of SQL — SELECT, WHERE, JOIN, and so on — looks nearly identical whether you're using MySQL, PostgreSQL, SQL Server, or Oracle. Each engine adds its own extensions and quirks around that shared core (you'll see MySQL-specific syntax called out as it comes up), but the fundamentals you learn this week transfer directly to any of them.

The language of databases

Just like English or French lets you talk to a person, SQL lets you talk to a database — ask it questions, and tell it what to change.

Declarative, not step-by-step

You describe what result you want, not how to compute it row by row — the database engine decides the fastest way to actually get it.

Still the industry standard

Five decades old and still how the overwhelming majority of business data is stored and queried, from startups to banks.

Why not just use Python/pandas?

You will, later — but pandas loads data into memory on one machine; a database can hold far more than that, is built for many people querying it at once, and enforces rules (like "an order must belong to a real account") that a loose CSV file can't. In practice, data analysts move data from a database into pandas with a SQL query, not the other way around. SQL is usually the first step, not a competing tool.

2What is a database?

A structured collection of data, organized for efficient retrieval.

A database doesn't just sit there holding data — it's managed by a DBMS (Database Management System), the actual software (MySQL, in this course) that writes data to disk, reads it back, and enforces the rules you define. When people say "the database," they usually mean both things at once: the data itself, and the engine running underneath it. Four things a DBMS is responsible for:

Data Storage

Stores data persistently on disk or in memory, ensuring durability and availability even after a crash or power failure — a plain in-memory Python list vanishes the moment the program stops; a database doesn't.

Data Retrieval

Lets you pull data back out efficiently: filtering, sorting, and aggregating, using indexes behind the scenes so a lookup on a billion-row table can still take milliseconds.

Data Manipulation

Lets you insert new records, update existing ones, and delete what's unwanted — safely, even while other people or programs are reading and writing at the same time.

Data Security

Enforces access control — authentication (who are you), authorization (what are you allowed to touch), and encryption, so not everyone with a login can see or change everything.

3Relational vs. non-relational

Two fundamentally different ways to shape data — and why this course picks one of them.

Relational (RDBMS)

Organizes data into fixed-shape tables of rows and columns, with relationships enforced between them via keys. Every row in a table has exactly the same columns — strict, predictable structure.

Best for: data with clear structure and relationships — orders, accounts, transactions, inventory. Queried with SQL — what this course uses.

  • MySQL
  • PostgreSQL
  • SQL Server

Non-relational (NoSQL)

Stores data as key-value pairs, flexible documents, or graphs. Two "rows" in the same collection can have completely different fields — loose, flexible structure.

Best for: large volumes of unstructured or fast-changing data — logs, session caches, content with wildly varying shape.

  • MongoDB
  • Cassandra
  • Redis
Why this course is relational

Data analysis is overwhelmingly about tables — sales by region, orders by customer, events by channel. The relational model's strict structure is exactly what makes it possible to ask precise aggregate questions ("total revenue per account") reliably. That precision is worth the flexibility it trades away.

4Database design: entities, attributes, relationships

The three building blocks every table design starts from.

Entities

The main data objects or concepts in the system — e.g. customers, products, orders, employees. Each entity usually becomes one table.

Attributes

The properties of each entity — e.g. customer name, product price, order date. Each attribute usually becomes one column.

Relationships

How entities connect — e.g. an order belongs to a customer, and a customer can have many orders. Enforced via primary/foreign keys.

5Three types of relationships

Established by a primary key and a foreign key — every relationship you'll ever model reduces to one of these three shapes.

The N:N case needs a junction table in the middle — book_author above — holding its own primary key plus the two foreign keys, because a foreign key can only point to one row, so there's no way to link "many books to many authors" with a single FK column on either side.

6CRUD & SQL statement types

Every operation you'll ever perform on a database — and every SQL statement you'll ever write — falls into one of a small number of buckets.

01 · Create

Create a database or table; insert a new record or column.

CREATE TABLE INSERT INTO

02 · Read

Select existing record(s) — the operation this whole lesson focuses on.

SELECT

03 · Update

Modify an existing table's data.

UPDATE ... SET

04 · Delete

Remove a record, column, table, or database.

DELETE FROM DROP TABLE

Zoom out one level further, and SQL statements themselves split into four formal categories — worth knowing the names even though this course lives almost entirely in the first one:

DML — Data Manipulation

SELECT, INSERT, UPDATE, DELETE. Working with the rows inside tables that already exist.

DDL — Data Definition

CREATE, ALTER, DROP. Building and changing the tables themselves — you've already run one DDL statement if you set up rawaj_db.sql.

DCL — Data Control

GRANT, REVOKE. Who's allowed to do what — relevant once a database has more than one user.

TCL — Transaction Control

COMMIT, ROLLBACK. Making a batch of changes permanent, or undoing them if something went wrong mid-way.

7Why SQL for data analysis

You manage a bookstore. Which books sold the most this month?

You could open the sales spreadsheet and manually tally rows — for a small shop, maybe that takes twenty minutes. Now imagine 50,000 transactions a month across 200 stores. Manual tallying stops being an option, and this is exactly the gap SQL closes:

motivating_example.sql
SELECT title, SUM(quantity_sold) AS total_sold FROM sales GROUP BY title ORDER BY total_sold DESC;
No manual digging

One query answers it, instantly, no matter whether the table has 50 rows or 50 million.

Scales to real questions

Top-sellers, revenue trends, average order value, new customers this month — same idea, every time: describe the shape of the answer you want.

A core analyst skill

This is how raw transactional data turns into a decision someone can act on. Don't worry about GROUP BY yet — Day 02 covers it properly; for now just notice how little code that question actually needed.

The same handful of ideas — filter, sort, group, aggregate — answers an enormous range of business questions: What are the top-selling products by quantity? What's the average order value? Which shipping destinations are most common? How many new customers did we acquire last month? Every one of those is a small variation on the query above.

10Anatomy of a SELECT

Every query in this lesson has the same skeleton — learn this shape once and you can read (and predict the structure of) almost any SELECT you'll ever encounter:

skeleton
SELECT <columns> FROM <table> -- [WHERE <condition>] not yet — Day 02 ORDER BY <column> LIMIT <count>;

Business question: marketing wants a first look at every customer on file — just first name, last name, and email to start.

day01_sql_foundations.sql
SELECT first_name, last_name, email FROM customers; -- SELECT * means "give me every column" SELECT * FROM customers;
Name columns explicitly

Clearer what the query returns, and it won't silently break — or silently return an extra unwanted column — if someone adds a column to the table later.

SELECT *

Fine for a quick look at a table you don't know yet. Risky to leave in real, shared work.

11LIMIT & OFFSET

LIMIT caps how many rows come back. OFFSET skips a number of rows before it starts counting — together, this is exactly how "page 2 of results" works on any website with a paginated table.

Business question: the team only wants to review one slice of the customer list at a time — show "page 2," 3 customers per page.

day01_sql_foundations.sql
-- standard SQL SELECT * FROM customers LIMIT 3 OFFSET 2; -- MySQL shortcut: LIMIT skip, count SELECT * FROM customers LIMIT 2,3;
Same result

Both return 3 rows, after skipping the first 2.

Prefer OFFSET

The shortcut form is easy to misread — is the first number the skip or the count? Most people default to the explicit OFFSET form for anything they'll hand to someone else.

12DISTINCT

Business question: before building a governorate filter for a dashboard, find out which governorates actually have customers registered.

day01_sql_foundations.sql
SELECT DISTINCT governorate_id FROM customers;
Collapses duplicates

Down to one row per unique value — without it, you'd get one row per customer, with each governorate's ID repeated for every customer registered there.

Answers a different question

DISTINCT asks "what are the possible values?" — not "what's the value for each row?"

Combine with COUNT

COUNT(DISTINCT governorate_id) collapses both ideas into a single number — how many unique values exist.

13Aggregation: COUNT

COUNT is your first aggregate function — instead of returning one row per input row, it collapses many rows into a single summary number.

Business question: a stakeholder asks three things at once — how many customers are in this dataset, how many actually have an email on file, and how many distinct governorates are represented?

day01_sql_foundations.sql
SELECT COUNT(*) AS customer_cnt FROM customers; SELECT COUNT(email) customers_with_email FROM customers; SELECT COUNT(DISTINCT governorate_id) AS governorate_cnt FROM customers;
COUNT(*)

Counts every row, full stop — doesn't care what's inside any particular column.

COUNT(col)

Counts only rows where that column is not NULL — some customers checked out as a guest and never left an email, so COUNT(email) comes back lower than COUNT(*).

AS is optional

COUNT(*) customer_cnt works identically to writing AS — but spelling it out is usually clearer to read back later.

14ORDER BY

Business question: the growth team wants a shortlist — the 5 customers who signed up earliest, Rawaj's very first adopters.

day01_sql_foundations.sql
-- 5 earliest customer signups SELECT first_name, last_name FROM customers ORDER BY last_name ASC LIMIT 5;
ASC is the default

Ascending order happens automatically — rarely written out. DESC (descending) is the one you'll see explicitly.

Sort by anything

You can sort by a column that isn't even in your SELECT list.

ORDER BY + LIMIT = "top N"

Together, these two clauses are how you answer almost any "top N" or "bottom N" business question.

Before you move on — common first-week mistakes

Forgetting the semicolon: MySQL clients often wait silently for more input instead of running your query if the trailing ; is missing — end every statement with it, always.

Assuming LIMIT 5 means "the first 5 rows": without ORDER BY, a table has no guaranteed row order — say so explicitly if order matters.

Reusing an alias in WHERE: SELECT signup_date AS joined FROM customers WHERE joined > '2024-01-01' fails — the alias doesn't exist yet when WHERE runs. Use the real column name there; aliases are safe in ORDER BY.
